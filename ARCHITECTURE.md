# Architecture

pravo is one Go binary, built from the module `github.com/pravo-systems/pravo`. The name `pravo.dev/pravo` that appears in specifications is something else: the CUE package that `pravo init` generates and every specification imports. It evaluates a CUE package, compares the result with a graph of recorded resources, and drives OpenTofu providers over the provider plugin protocol. This file describes how the code is arranged. The behaviour that users rely on is documented in `docs/`.

```text
 *.cue files             internal/config          internal/convert
 one CUE package  --->   load, discover    --->   CUE values <-> provider values
                                 |
                                 v
 internal/state   <---   internal/engine    --->   internal/plugin   --->   provider binary
 records, locks          graph, plan, apply        protocol 5 and 6          separate process
 transactions            policies, saved plans
```

## 2. The life of a run

A command that evaluates the specification passes through these phases.

| Phase | Where | What happens |
|---|---|---|
| Start | `main`, `newRootCmd` | `normaliseArgs` rewrites single-dash long flags to double-dash. `telemetry.Setup` installs exporters. `PersistentPreRunE` configures `plog`, the printer (standard output; standard error under `--json`), the actor and reason (`--actor`, `PRAVO_ACTOR`, `--reason`, `PRAVO_REASON`) and `-C`. `startCommand` opens the command span. |
| Policies | `Engine.planPolicies`, `Store.PolicySet` | `plan` compares the `pravo.#Policy` nodes of the root with the versions in force in the state (`PolicyEntry`, counted by `PolicyCounts`). `checkNewPolicy` compiles each new or changed rule and runs it on the document of an empty plan. A root that declares a policy on a state that is not sealed fails with exit 5. `apply` writes the new versions (`writePolicies`, `PutPolicyVersion`) after it judges. |
| Load | `loadRoot`, `config.Load` | `checkPackageClauses` rejects a file outside the package. `ConfigureRegistry` sets a default `CUE_REGISTRY`. `load.Instances` applies `-t` tags and `-T` system tags. `BuildInstance` and `Validate` evaluate. `collectTree` records the module root, every loaded file and the dependency modules with content hashes. A failure exits 6. |
| Discover | `Root.extract` | `extractSettings` reads `$settings` (`state` and `refresh`; any other key is an error). `discover` and `walk` visit every field except `$settings`. `register` records each struct that carries `$kind`: `resource`, `data`, `ephemeral`, `call`, `provider`, `output`, `env`, `secret_env`, `remote_outputs`. It collects `$from` and `$import`. `resolveProviders` gives each provider struct an instance key and each resource its provider. `walk` refuses a required provider field that no instance filled (`provider docs.tls was not supplied`), and `resolveProviders` refuses configuration on a struct that shares another struct's instance (`extraConfig`). |
| Session | `newSession` | `engine.ReadLock`; `openState` or `openStateReadOnly`; `NewProviders`; `Providers.Resolve`; `Lock.UpdateModules`; `writeLock`; `warnStaleSchemas`; `Providers.Schemas`. |
| Engine | `session.engine`, `engine.New` | Builds the `Engine` with the root, state, providers, schemas and options. `SetPolicies` compiles the policies in the root's CUE context. |
| Graph | `Engine.run`, `buildGraph` | See section 2.1. |
| Plan | `Engine.Plan`, `planRun` | See section 2.2. |
| Judge | `Engine.JudgePlan`, `Engine.JudgeFile` | See section 2.3. |
| Apply | `Engine.Apply`, `applyRun` | See section 2.4. |
| Record | `state.Store`, `state.Txn` | See section 3. |
| Finish | `exitCodeOf`, `finishCommand` | The error is mapped to an exit code (`engine.ExitCode`: 1 error, 2 changes, 3 stale, 4 locked, 5 refused, 6 invalid). Duration and rejection reasons go to telemetry. |

### 2.1 Graph and scheduler

`buildGraph` creates one node per declared resource, data source, ephemeral resource, function call and built-in (`pravo.#Env`, `pravo.#SecretEnv`, `pravo.#RemoteOutputs`). An edge comes from `convert.Dependencies`, which reads the expression tree of each body and follows references through interpolation, calls, arithmetic, comprehensions and intermediate fields. A reference to a struct or list that holds resources, and is not itself a resource, is an edge to every resource below it, whether it is a comprehension source, an index, an argument or an entry of `$depends_on`; the struct that holds the referencing resource is not an edge. `convert.Resolver` is the interface through which the engine answers what is a resource, what lies below a path and what a plain field holds. `$depends_on` adds references. A resource also waits for whatever its provider's configuration references (`providerDeps`). `checkCycles` removes nodes whose dependencies are done; the remainder is grouped into strongly connected components, and each group of two or more is reported as `dependency cycle between ...` with exit 6. `CheckGraph` runs the same build for `validate`.

`run` starts a goroutine for each node whose dependencies have finished, at most `Parallelism` (10 unless `PRAVO_PARALLELISM` sets it) at once. All CUE evaluation and filling is serialised by `Engine.cueMu`. Only provider calls run concurrently. The first error cancels the context of the run: no further node starts, a node whose task has not begun is counted, and a run that stops with no error of its own because its context was cancelled fails with `interrupted: N of M tasks were not started`. A call that changes an object is not cancelled with it (section 2.4). `closeEphemerals` closes every ephemeral resource that the run opened.

Each node runs `runTask` in a span, then `runTaskInner`:

| Mode | Function |
|---|---|
| built-in | `builtinTask`: `envTask` reads an environment variable; `remoteOutputsTask` reads another root's `outputs.json`. |
| `call` | `callTask`: converts `args`, calls the function on an unconfigured provider when the arguments are known, fills `result`. |
| `ephemeral` | `ephemeralTask`: validates, opens, renews on the provider's deadline in `renewLoop`. |
| `managed`, `data` | `planTask` or `applyTask`, both through `planResource`. |

After a node runs, `convert.Fill` computes the provider's values for every part of the body that is not yet concrete, and `Engine.fill` queues them; `settleAllLocked` unifies the queued fills into the current value in one step, when a task that reads them starts or when the run ends. Dependents of the node then see concrete values. The fields of a struct are in the order in which they were first met, and a fill meets a field before the comprehension that declares it does, so the order of a container of nodes would follow the order in which the nodes finished. `below` notes every container of nodes that something reads, and the first batch of fills of a run starts with `seedFills`: an empty fill for each node below such a container, in the order the specification declares them. A comprehension over the container visits the nodes in that order, in the plan and in the apply of it.

### 2.2 Plan

`planRun` does the following in order:

1. `checkOutputs` refuses an output that references an ephemeral value. `checkReplace` validates `--replace`. With `--destroy`, `checkDestroy` builds the graph and applies `prevent_destroy`.
2. `State.Begin("plan", command)` starts the transaction.
3. `relabelProviders(true)` and `applyMoves(ctx, true)` stage what the specification declares: a provider `$from`, the records that `$from` moves (`stageMove`, which rewrites the dependencies of other records) and the objects that `$import` reads (`importResource`). A staged record lives in the memory of the `Store` (`Stage`, `StageRemove`; `Get` and `Verify` see it, a `Set` of the plan does not write it) and the plan lists it as a `move` or an import. The plan writes nothing of this; `Plan.HasDeclared` is true, `Plan.HasChanges` is not, and `Plan.HasWrites` is either. The apply drops the staged records (`DropStaged`) and writes them: `commitMoves` before `lockAll` (`moveNode`, then `retarget` points the plan at the new revisions) and `commitImports` once the locks are held.
4. `run(ctx, false)` walks the graph.
5. `planOrphans` plans a delete for every record whose address the specification does not declare (`planDelete`), ordered with dependents first (`orderForDestroy`). With `--destroy` it plans a delete for every record and nothing else runs.
6. `renameHints` pairs a create and a delete of the same type and configuration hash.
7. Outputs are evaluated (`canonicalOutput` sorts struct keys).
8. `checkReservations` and `reserve` apply and take reservations.
9. `Txn.Finish("planned", ...)` writes the transaction when it recorded a change.

`planResource` plans one managed resource or data source:

1. `convert.Converter.Block` converts the body against the provider schema. A concrete value is the value. An absent optional field is null. A non-concrete value that references a task is unknown, or an error at apply time (`Strict`). A non-concrete value that references no task is null, or an error when it depends on an incomplete value outside any task. `configHash` hashes the result when it is fully known.
2. The node is unchanged when the record exists and carries no mark (`Resource.Marked`: `drifted_at` or `gone`), `--full` and `--replace` do not apply, the hash equals `config_hash`, and the schema version, provider version and provider key equal those recorded. An apply that stopped halfway stored an empty `config_hash`, so the node is changed, with the reason `the last apply of it did not finish`. A different key adds the reason `provider instance changed (A -> B)`; the plan still proposes no change to the object, and the apply writes the record again (`writeState`).
3. A data source that is unchanged, has no dependency with a pending change and is not due for refresh reuses its record. A data source whose configuration is unknown, or with a pending dependency, is deferred to apply. Otherwise `ReadDataSource` runs. A read of an unchanged data source that returns the attributes, edges and provider of its record (`recordHolds`) sets `Change.Kept`: `Change.writes` is false for it, so the plan does not list it in `Plan.Write`, the apply takes no lock and writes nothing for it, and the nodes that read it take its record (`roleInput`). `renewData` writes the time of that read with `Store.Refresh`, which keeps the revision, when the refresh age is a duration, no other process holds the lock and the record in the state is still the one the command read; with `always` or `never` nothing is written.
4. An unchanged node with a record that this run has not read is turned into a skipped no-op by `quiet` in `RefreshAge` (and in `RefreshNone` outside the apply): the plan starts no provider for it, does not call `UpgradeResourceState` or `ReadResource` and writes nothing, whatever the age of its record. `quiet` does not skip a node that sets its own `$lifecycle.refresh` and is past it, nor one that `readReason` names (below). The record is decoded into `Change.Prior` and `Change.Planned` (`storedValue`) only when `Engine.readers` has the node, a set that `buildGraph` makes of the nodes that something reads: a dependent, the configuration of a provider or an output. A node nobody reads is not decoded and not filled into the configuration; the constraint of a user on its computed attributes is checked when the node is next planned. For any other node with a record, `priorState` calls `UpgradeResourceState`, then `ReadResource` when `refreshDue` says so, and a read made earlier in the run (`cachedRead`) is used in place of a second one. The refresh age is `$lifecycle.refresh`, else `$settings.refresh`, else `always`. `RefreshExpired` skips `quiet` and reads every node whose age has run out; `RefreshAll` and `RefreshNone` override the ages. `persistRefreshed` writes the refreshed record when no other process holds its lock and the record in the state is still the one the command read (`Store.Refresh`); a read that returns other attributes also writes `drifted_at`, and `persistGone` writes `gone` and `drifted_at` for an object that does not exist.
5. An unchanged node with a record, and no drift, becomes a skipped no-op.

In `RefreshAge`, `planRun` calls `readInputs` after the walk. It reads in parallel (`Parallelism`) the nodes that a reached node reads, that were skipped without a read and whose record is past its age (`readInput`). A read that finds other attributes or no object writes the mark and the plan walks again from the records as they are now (`rewalk`, `run`), with every read already made kept in `Engine.reads`. Each walk reaches the nodes that the marks make reachable, and reads one level of their inputs, so a chain of changed records takes one round for each; the rounds end when a read finds nothing. A record found changed in a round after it was found changed in an earlier one fails the plan with `changed while the plan read it; run pravo plan again`, and the marks it wrote stay for the next plan. `countUnread` then counts the nodes that were not read as `Stats.Fresh` (within their age) or `Stats.NotRead`. `pravo drift --due` calls `Engine.DriftDue`: it visits the managed records, reads the ones past their age, the oldest first and at most the limit of them, writes what it reads and the marks, and plans nothing. Before the reads, `fillProviderInputs` sets up the providers of those records as a plan does: it walks the nodes their configuration reads with an `applyScope`, a managed or data node that has a record as `roleInput` (its value is its record, and only what its own configuration reads comes with it), and a built-in value, ephemeral resource or function call as `roleSupport`, which runs. `keepOpen` leaves the ephemeral resources open for the reads, and `DriftDue` closes them. A record that a provider is set up from and the state does not hold is an error.

`readReason` names the three reasons for which a plan reads a record whatever its refresh age, in the modes that read by age (`RefreshAge`, `RefreshExpired`). `quiet` does not skip such a node, `priorState` reads it, and `Change.forced` is the reason it prints; a data source takes the same path. The first reason is a stale lock on the node: `loadSuspects` calls `Store.Suspects` once per plan, which lists the locks and returns the stale ones that are not reservations, and the read that follows removes the lock, because `persistRefreshed` takes the node's lock with `TryHold`, which reclaims a stale lock. With `-refresh=false` `warnSuspects` prints a warning and nothing is read. The second is a provider that points somewhere else: every record written by an apply, a refresh or an import carries `provider_config`, the digest `providerTarget` works out, once per walk and provider instance, from the configuration of the instance (`providerConfig`) and the provider schema, without starting the provider. `targetBlock` leaves out an attribute that is sensitive or write-only, one that references an ephemeral resource and one that is unknown; a configuration with an unknown value has no digest (`ok` false) and neither forces a read nor is stamped, and an instance with no attribute left has the empty digest, which no record carries. A record whose digest is not empty and differs from the one of its instance now is read, and planned only if the read finds drift. A record with no digest forces nothing. The third reason is a record that an apply wrote and that has no `refreshed_at` (`Resource.NoReadTime`), which is what `unsettle` leaves; `priorState` takes `readReason` also for a node whose age has run out, so that the plan says why it read the node. With `-refresh=false` `warnSuspects` prints a warning for these nodes as well. `Store.Refresh` does not count a change of `provider_config` as a change of the record.
6. `ValidateResourceConfig`, `applyIgnoreChanges`, `ProposedNew`, then `PlanResourceChange`. The action is create (no prior), replace (`requires_replace` and a changed planned state, or `--replace`), no-op (planned equals prior) or update. A replacement plans the create again from a null prior (`PlannedCreate`).
7. `applyIgnoreChanges` copies the prior value over each top-level attribute named in `ignore_changes`, or over all of them for `"*"`. `ProposedNew` (`proposed.go`) merges prior and configuration as OpenTofu core does: the configuration wins, and a null configuration value for a computed attribute inherits the prior value. `withoutWriteOnly` removes write-only attributes before a plan is saved.

Each `Change` carries `Reasons`, the sentences that `pravo why` and the plan document print.

### 2.3 Judge and saved plans

The command prints the plan before it judges it. `NewView` builds the plan document (`View`, with `Summary`, `Stats`, `ChangeView` entries, `Outputs`, `Hints`, `Providers`) and the blast radius from `State.Reach`. The document lists the nodes the plan ran; with `ViewOptions.Skipped` it lists the others too, each as an entry built from the record in the state (`withSkipped`). `ui.Printer.RenderPlan` prints it as text; `emitJSON` prints it under `--json`. A policy does not judge that document. `judgedDoc` builds the judged document from the plan file alone: the view without `blast_radius`, `dependents`, `hints` and `trace_id`, with the applied marks cleared and `changes` as a list. It converts it to a CUE value (`cuejson.Extract`), and `judgeVersions` unifies each version in force (`PolicySet.InForce`) with it and calls `Validate(cue.Concrete(true))`. A plan that changes no resource is not judged. `JudgePlan` is what `plan` calls, for feedback. `judgeApply` judges under the locks at apply, and the versions that judged go into the signed start of the transaction (`receipt.go`; `pravo state verify` checks them with `VerifyReceipt`). A failure is exit 5 and nothing is applied. A policy that is satisfied prints `Policy NAME@SEQ:<sha-256> is satisfied.`

`SavePlan` writes a `PlanFile` (format 1, mode `0600`): the change of every node the plan ran, with provider values as msgpack, the config fingerprint (`Root.Fingerprint`), the state lineage, provider versions, tags, the revision of each node it changes and, in `inputs`, the revision of every record those changes read, and the outputs it evaluates (`eval_outputs`) and removes (`drop_outputs`). A node the plan left alone has no entry. `apply <planfile>` runs `ReadPlanFile`, `LoadPlanFor` (which returns `ErrStalePlan`, exit 3, when the fingerprint, lineage or a provider version differs, when a node the apply writes, or one of the selected nodes with `--only`, has another revision, or when an input has another revision; a file of format 1 lists no inputs, so `legacyInputs` takes the revisions of the records that the changes read, as `scopeFor` finds them, from the entries of the file for the nodes the plan left alone), `Plan.Remaining`, `PlanFile.LeftToApply` (a change to a provider, or records and outputs that no apply from the file has written, which `apply_txn` records), `JudgeFile` on the whole file, `Plan.Subset` for `--only` (the selection must be closed under dependencies, else `ErrNotClosed`; a data source whose read returned something other than its record counts as a dependency to select, `needed`), `ApplySaved`, then `MarkApplied`, which locks the plan file (`flock`), marks the changes in the file as it is then, not in the copy the apply loaded, and writes it by a rename: applies of disjoint parts of one file that run at once keep every mark, and a file that holds another plan (another `created`, lineage or fingerprint) is left as it is. `ApplySaved` hands the engine the changes to apply and the answer of each data source the plan read (`rememberData`), so that the walk reads no data source again. During apply, `checkSaved` compares each re-planned change with the saved one: the same action or nothing left to do, every planned value that the saved plan knew (`consistent`), the data of a data source, and, for a node with nothing left to do, that its record holds what the saved change would have made. The apply of a plan that the same run printed makes the same comparison. A difference is exit 3 for both. The comparison runs in the walk, as it reaches each node, so nodes applied before the one that differs keep their changes and the plan file is not marked.

### 2.4 Apply

`applyRun` runs one transaction of kind `apply` or `destroy`:

1. For a destroy, `checkPreventDestroy`.
2. `lockAll` returns the `heldLocks` that hold the lock of every record in `Plan.writeAddrs`, and of no other, before the first change. `heldLocks.acquire` takes the first address alone and the others 16 at a time, each group after the one before it (`heldLocks.attempt`). An apply never holds some of its locks while it waits for the others. When another process holds a lock, the locks taken are released at once and `heldLocks.waits` decides whether to look again: a lock whose transaction has the status `running` (`Store.TxnRunning`), and a reservation, reject the apply with exit 4; any other lock may belong to an apply that is taking its own locks and releases them if it meets another, so the apply looks at the lock with `Store.Conflict` until it is free, for `patience` (ten times the time one try took, between `minPatience` and `maxPatience`), and tries again. The addresses that were held (`contested`) are then taken first, one at a time and in order, so that applies that meet at the same nodes meet at the first of them, and a random pause that grows with each round keeps applies that were turned away together from meeting again. An apply is rejected only because a lock is held by an apply that took it, or when the patience is spent. `heldLocks.rejected` looks at the locks the apply needs, in order and for at most `scanTime`, so that the error names the smallest address that is held and counts the others (`at least` when it did not look at all). A goroutine renews the locks every `state.HeartbeatInterval`, 16 at a time, with `Store.Renew`. Before each `ApplyResourceChange`, `heldLocks.fence` renews them if more than half of `state.StaleAfter` has passed since every lock was last known to be the apply's; a lock that another process has taken over is exit 4, `lock lost`. `checkRevisions` then reads the version, the revision and the generation, of every record the plan writes (`Change.PriorRevision`, `Change.PriorGeneration`) and every record of the scope that the plan lists as read (`Plan.Inputs`, `Plan.InputGenerations`, narrowed to the inputs of the scope by `applyScope.inputsOf`, so that the part of a saved plan applied with `--only` checks the records it reads) with `Store.Versions`, 16 reads at a time, which asks the backend and not the nodes the store loaded when the command started. A record at another revision, or in another generation because it was removed and created again, is exit 3 before anything changes: `ErrStalePlan` for a plan loaded from a file, `the plan changed while it waited` for the plan the command printed. The transaction is recorded as `rejected`. Otherwise an apply that locked a node writes its transaction with the status `running` (`Txn.Start`) before the first change.
3. Unless destroying, `scopeFor` computes what the apply walks: the nodes the plan writes (`Plan.Write`), the records they read and, because a field of a record can be an expression over the nodes it reads, the records those read in turn, which run as `fromState` (`roleInput`), and the ephemeral resources, function calls and built-in values they read, with what those read (`roleSupport`). `applyScope.nodes` makes the graph of the scope: each node waits for the nodes of the scope that it reads, directly or through nodes outside the scope, and a record is one of them. What `fromState` fills in from a record then meets the values that the apply writes, and `snapshot` unifies the pending fills of those nodes before the task starts. `resetRun` and `run(ctx, true)` walk that part of the graph, which `buildGraph` built once, on a fresh evaluation. `applyTask` calls `planResource` with `Strict` and known values, then performs the action through `applyChange` (`ApplyResourceChange`) and `writeState`. A plan made by the same run reads nothing again: `readResult` and `dataRead` hold what the plan read. A replacement is destroy then create, or create then destroy with `create_before_destroy`. A partial state returned with an error is written. `applyChange` calls `ApplyResourceChange` on `context.WithoutCancel`: a node that fails, or a signal, stops the walk from starting nodes, and a call that has begun finishes and its state is written before the locks are released. `Engine.fly` and `land` keep the nodes whose call is under way. A call that fails, that ends with an error and no state for an update or a destruction of a node that has a record, or that ends with an error and no state after the providers were asked to stop, leaves a change whose result is not known: `unsettle` writes the record again with `Store.Invalidate`, which clears `refreshed_at` and moves the revision, records the action `unsettled` in the transaction, and `withUnsettled` adds `creation of X was in flight; its result is unknown; check the provider` to the error (`creation`, `update` or `destruction`). A creation that has no record has none to write. A write of the record that fails after the provider finished the change (`recordApplied`, and the removal of the record after a destroy) is noted by `unrecorded` in the same way, with `creation of X finished, but the state does not record it; check the provider`; the error of a partial state that cannot be recorded names the failure of the provider and the failure of the write.
4. Deleted records are destroyed in the order the plan fixed. Data records are only forgotten.
5. The outputs in `Plan.EvalOutputs` (those that read a node the plan writes, those the plan could not tell and those whose value differs from the recorded one) are checked for concreteness; the others keep the recorded value. A recorded output that the specification does not declare (`Plan.DropOutputs`) is removed. `State.LoadOutputs` reads them and says whether `outputs.json` exists. When the outputs have changed or the object does not exist yet, `State.UpdateOutputs` takes the lock object `outputs.lock`, reads the outputs again, and `mergeOutputs` merges the apply's outputs into them before they are written, so that two applies that end together keep each other's outputs; a sensitive output is stored as `{"$sensitive": value}`. A plan that writes no node, no output and removes no output is not applied: no lock, no record, no transaction.
6. `Txn.Finish("applied", ...)` replaces the running transaction; `release` stops the heartbeat and removes the locks, 16 at a time, each after a check that it is still this process's.

`cmd/pravo/main.go` handles `SIGINT` and `SIGTERM` in stages (`watchSignals`) through an `engine.Interrupt` that the context of the command carries and `applyRun` registers with (`register`). The first signal cancels the context and prints `Interrupted. Waiting for N operations; interrupt again to ask the providers to stop.` with the number `Interrupt.InFlight` gives. The second calls `Interrupt.Stop`, which calls `Providers.StopAll`: `Stop` on every provider that pravo started, not on a reattached one, so a provider returns the state it had reached; it waits up to 30 seconds (`interruptGrace`). The third, or the end of the wait, or the second when nothing is in flight, calls `Interrupt.Abandon`: `Engine.abandon` makes `unsettle` of every call still under way, writes the transaction as `failed`, releases the locks, and the process exits with code 1. `watchSignals` waits for `Abandon` for `abandonWait`, 20 seconds, and exits without it when the state does not answer. The state is opened with the context that the first signal cancels, and its calls after the opening do not end with that context (`state.OpenBackend`), so the records, the transaction and the locks are written to a bucket after a signal as they are to a directory. A process that is killed does it none of this, and its locks go stale.

### 2.5 Stored plans

`plan --store` keeps a plan in the state (`internal/engine/planstore.go` and `plangc.go`, `cmd/pravo/planstore.go`). `Engine.StorePlan` builds the `PlanFile` that `SavePlan` writes (`buildPlanFile`), and `PlanStore.Put` writes `plans/<id>.plan.json` with `PutIfAbsent` and then `plans/<id>.meta.json`, so a plan with no summary is a write that did not finish. The id is `plan-` and the first eight hexadecimal digits of the SHA-256 of the plan bytes (`digestID`): the same bytes keep their id, and another plan with the same eight digits gets a longer one. `PlanMeta`, built by `newPlanMeta`, is what a listing reads: the author (the actor, else the user of the machine), the expiry (`created` plus the time to live, `DefaultPlanTTL`), the counts, the resources touched and, in `Bases`, the revision and generation of each record the plan writes or, with `Reads`, only reads. `plans/<id>.progress.json` (`PlanProgress`) is the one object that changes. `updateProgress` creates it with `PutIfAbsent`, or edits it through `ReplaceIf` and tries again when it lost a race. It holds `Applied` (address to transaction), `ApplyTxn`, `DoneAt`, `StaleSince` and two kinds of claim: `Applying`, a list with one claim for each apply that runs from the plan, each honoured for 24 hours, and `Collecting`, held by a collector and honoured for 10 minutes. A claim is named `actor@host#pid.token` (`collector`). `PlanMeta` counts reads as the plan does and lists a read only when the apply makes it (`Deferred`).

`Entries` reads the summaries and the progress objects, several at a time and asking only for the objects that the listing shows, and leaves out a plan whose summary or progress cannot be read. `planStatus` gives the verdict in this order: `applied` (`DoneAt` is set), `expired`, `stale`, `partly-stale`, `partial`, `pending`. Staleness is judged against the state alone (`PlanCheck`: `Store.Lineage`, and `Store.Versions` for the records of `Bases` that no apply from the plan has written, read once however many plans expect them). A lineage mismatch, a record that the plan reads (`Bases` with `Reads`) and a record that no apply of a part takes as a change (`selectable`) that moved make the whole plan stale. Any other record that moved is a conflict of one change: `judgePlan` blocks that change and the changes that have to be applied with it (`PlanMeta.Needs`, the one-step relation that `Plan.Subset` uses, kept in the summary), and the rest is `Live`, the closed set that `apply --only` accepts (`PlanEntry.ApplyLiveCommand`). A plan with live and blocked changes is `partly-stale`, and is open; a plan with nothing live is stale; a summary without `Needs` is judged as a whole. The fingerprint and the provider versions are compared by `LoadPlan`, when a command shows or applies the plan. `Overlaps` finds the open plans that still change a resource the new plan changes (`touchedBy` leaves out what a plan applied, and names a resource once), and `plan` warns about them. `applyStored` resolves the id (`Resolve`), checks the `-t` and `-T` against the plan (`planTagsMatch`: they select the state), refuses a plan that was not applied and has expired with exit 3, takes the claim of this apply (`BeginApply` keeps the claims of other applies and fails with `ErrPlanRemoving`, the only claim error that is exit 3, while a collector holds the plan) and gives `applyPlanFile`, which `applySaved` shares, the plan from `ReadFile`, with the changes in `Applied` marked. Its `mark` callback is `MarkApplied` when the apply returned without an error. When it failed or was interrupted, `recordPartial` calls `MarkPartlyApplied` with `ApplyResult.Applied`, the changes that the apply finished and recorded (`Engine.complete`), and says what to do with the rest by judging the plan again. It sets `DoneAt` when every change that was pending when the apply began is in `Applied`, whichever apply wrote the last. `MarkApplied` and `EndApply`, which ends only this apply's claim, run with a context that outlives an interrupt.

`PlanStore.GC` applies `gcRules` to each plan: an applied plan after `DefaultAppliedKeep`, an expired plan, an unapplied plan older than `OlderThan`, and a stale plan when more than `DefaultStaleGrace` has passed since a collection first saw it stale (`StaleSince`; the first collection only marks). A partly stale plan is left to its time to live and loses a mark that it carries. `PlanClaim.Committed` closes the window between a collector's claim check and its deletes: `remove` writes it, by `updateProgress`, only while the claim is its own and no apply runs, and `BeginApply` refuses a committed claim whatever the clocks say (`holds`); another collection adopts a committed claim that has not been renewed for `claimTimeout` (`adoptable`). `KeepApply` renews the claim of a running apply every `applyRenewEvery`. `planInUse` keeps a plan an apply runs from (any claim in `Applying`), a plan that a collector holds and a plan with a reservation. A removal first claims the plan: `remove` judges it again inside `updateProgress`, so an apply that began meanwhile is respected. It then deletes the plan, the summary and the progress object with `DeleteIf`, each only if it is what its name says (`deleteObject`: the digest gives the id, the summary names the id, the progress object carries this collector's claim). `planObject` admits only the exact names of plan objects, so nothing else below `plans/` is listed or deleted. A summary that exists and cannot be read leaves the plan alone, and a progress object that cannot be parsed is made empty by `repairProgress` once the plan is older than an hour. `plan --store` calls `GC` with `Limit` 25 and `Skip` set to the plan it stored. `remove` reports a plan only when this call deleted one of its objects. A dry run marks nothing, and `plan gc` opens the state for changes only when it holds plan objects.

## 3. State store

`state.Store` holds every record in memory and writes through a `Backend`. `OpenBackend(ctx, b)` uses `ctx` to open the store; every call to the backend after that is made with `context.WithoutCancel(ctx)`, since a command that is interrupted still has to record what it did. The `Backend` interface is: `Get`, `Put`, `PutIfAbsent`, `DeleteIf`, `ReplaceIf`, `Delete`, `List`, `Name`, `Local`. `LocalBackend` writes each object to a temporary file of its own (`os.CreateTemp`, named after the key and ending in `.tmp`, which `List` skips) and renames it, so two writers of one key do not share a file. It creates a lock by writing the temporary file whole and renaming it to the key without replacing (`renamex_np` with `RENAME_EXCL` on macOS, `renameat2` with `RENAME_NOREPLACE` on Linux), or linking it where the filesystem cannot, so a lock that exists has all its contents; only a filesystem with neither gets `O_EXCL` followed by a write. `DeleteIf` and `ReplaceIf` open the object, take an exclusive `flock` on the file they opened, check that the name still refers to that file, read it, and delete it or write the new contents over it: of callers that judge the same lock, one acts, and a lock that was replaced after it was judged is left alone. `S3Backend` uses the AWS SDK with optional endpoint and path-style addressing, creates locks with a conditional put (`If-None-Match: *`), and implements `DeleteIf` and `ReplaceIf` as a read of the object and a delete or a put conditional on its entity tag (`If-Match`). A store that ignores either condition lets two commands that judge the same lock both act on it. `$settings.state` selects the backend; `openStateStore` builds it. `openStateReadOnly` wraps a backend so that commands that only look write nothing, not even `meta.json`.

`Set`, `Refresh` and `Remove` encode and write outside the mutex that guards the maps of the store, so a read of the graph does not wait for a backend. One of 64 mutexes, chosen by address, orders the writes of one record. The revision, the generation and the times are set on a copy; the node of the store is replaced, and the node that was passed in is updated, only when the backend has acknowledged the write, so a write that fails changes nothing in memory. `Refresh` reads the record from the backend once more, under the stripe, and writes nothing and returns `ErrChanged` when its revision or generation is not that of the node the store holds; `Engine.recordRefresh` prints a warning in that case. `Verify` is the same check for a command that rewrites a node from the copy it holds, and `LockDependents` locks the records that depend on a node and verifies them, for `moveNode` and `state mv`, which rewrite the dependencies of those records. In format 2 `Set`, `Refresh` and `Remove` also return `ErrChanged` when the pointer in the backend is not at the revision and generation the store holds, which in format 1 the last writer overwrote. The local backend acknowledges a write once the file is renamed into place and does not flush it to disk.

```text
<state>/
  meta.json                format (1, 2 or 3), lineage, creation time; in format 3 also sealed, migration, history
  resources/<addr>.json    one record per resource or data source in format 1; a pointer to a record in formats 2 and 3
  rec/<sha256>             formats 2 and 3: one immutable record, named by the hash of its bytes
  outputs.json             recorded outputs
  outputs.lock             present while a command updates outputs.json
  txn/<id>.json            one file per recorded transaction
  locks/<addr>.lock        one file per lock or reservation
  plans/<id>.plan.json     a stored plan, in the form of a plan file; written once
  plans/<id>.meta.json     its summary, which a listing reads; written once
  plans/<id>.progress.json what was applied from it, and who applies or removes it; replaced through ReplaceIf
```

`<addr>` is the CUE path of the resource. `encodeAddr` writes every character other than letters, digits, `.`, `_` and `-` as `%` and four hexadecimal digits.

The store has three formats (`Format`, `FormatImmutable`, `FormatSealed`; `MaxFormat` is the highest this build reads, and `openBackend` refuses a store above it with "written by a newer pravo"). A new store is format 1 unless `Options.NewFormat` says 2; `NewStoreFormat` and `NewStoreIdentity` are the variables that the test helpers set (`PRAVO_TEST_FORMAT=2` or `3`, read by `statetest`) to run a suite over stores of format 2, or over stores sealed to one identity. Format 1 is the layout above, byte for byte. In format 2 (`record.go`) `putNode` writes the record with `PutIfAbsent` under `rec/<sha256 of its bytes>` and then the pointer `{v, address, revision, generation, record}`: with `PutIfAbsent` for a node the store did not hold, otherwise with `ReplaceIf` whose closure accepts only a pointer (or a whole record) at the revision and generation the store holds (`nodeRef`, kept per address in `Store.held`). `ReplaceIf` reports false both for a refused closure and for a lost race on a bucket, so the closure sets a flag: a refusal is `ErrChanged`, a lost race reads again, up to `replaceAttempts`. A write that leaves the revision deletes the record it replaced, found from the pointer that was replaced. `Remove` is a `DeleteIf` on the same compare. `readNode` accepts a pointer or a whole record under any format, checks `sha256(bytes)` against the name and the address, revision and generation of the record against the pointer, and returns `ErrUntrusted` on a mismatch; a record that is not there is read again from the pointer, up to `readAttempts`. `Upgrade(To: 2)` replaces `meta.json` first (`updateMeta`: a `ReplaceIf` on the bytes read), then turns each whole record into a record and a pointer in `convertNodes`, 16 or 32 at a time, each by a compare-and-swap on the bytes it read, and can be run again. `VerifyAll` hashes every record and checks every pointer without a key.

Format 3 (`seal.go`, `seal_upgrade.go`) seals `attributes`, `private`, `config_hash` and `provider_config` of each record as one `protect.Sealed` in the record (`sealedRecord`; `sealedBody` is the plaintext), with `protect.Ctx` binding lineage, group, kind, address, generation and revision, and the whole of `outputs.json` as `{"v": 1, "sealed": ...}`. `meta.json` holds `protect.Meta` under `sealed`, a `migration` while a seal is under way, and the last 50 entries of `history`. `openSealed` unlocks the data keys with `Options.Identity` once; no identity, or one without a lock, sets `Store.locked`, and `writable` then returns `ErrNotReader` for every write; while `migration` is set it returns `ErrSealing`. `Upgrade(To: 3)` flips `meta.json` to format 3 with the marker, seals each record through `convertNodes` (a record that is already sealed is skipped, so a crash is finished by running it again), seals the outputs, calls `UpgradeOptions.Plans`, deletes the unnamed records that hold plain text (`sweepRecords`) and clears the marker. `Rewrap` calls `protect.Meta.Rewrap` inside `updateMeta`, and with `All` seals every record, the outputs and, through `RewrapOptions.Plans`, the stored plans again under the current group. `putNode` calls `recheckSeal`, which reads `meta.json` at most every `sealRecheck` (30 seconds) and switches to a new current group. `Store.Sealer` gives the plan store and the command lines the same keys; `Store.Protection` is what `pravo protect status` and the viewer render. `Store.GC` (`gc.go`) deletes the records that no pointer names once the newest time they show in the clear is older than a grace (`GCGrace`, 24 hours and never under `sweepGrace`) and an earlier collection at least `GCSettle` (15 minutes) before found them unnamed: that collection only marks, in `gc/marks.json` (`readMarks`, `writeMarks`: `PutIfAbsent` to create, `ReplaceIf` to merge, the marks of records that a pointer names or that are gone dropped; a dry run writes none), because a writer that copies records with the times they already have (`rewrap --all`, `protect init`, `Copy`) is not covered by the grace. It lists the pointers again before the delete and uses `DeleteIf` on the bytes it judged. With `GCOptions.Groups` it counts what is sealed in each group other than the current one (the records, the spared records, `outputs.json` and, through `GCOptions.Plans`, `PlanStore.SealedGroups`) and drops the groups with no count through `protect.Meta.Prune` inside `updateMeta`. `Copy` carries `rec/` but not `gc/marks.json`, and deletes the one in the destination, copies `meta.json` first when the state is above format 1, and refuses to replace a state that holds records with a sealed state of another lineage, or a sealed one with an unsealed one.

A record (`state.Resource`) holds `addr`, `mode`, `type`, `name`, `provider`, `provider_key`, `provider_protocol`, `provider_version`, `schema_version`, `attributes`, `private`, `dependencies`, `config_hash`, `provider_config`, `revision`, `generation`, `refreshed_at`, `applied_at`, `updated_at` and `txn`. `Set` increments the revision and gives a record that has no generation the id of its transaction, which a record that is removed and written again has too, at revision 1; a record written before generations were recorded has none until `Set` writes it. `Refresh` keeps the revision and the generation when only timestamps differ. Dependents and the blast radius are derived from `dependencies` (`Dependents`, `Reach`, `Edges`). A record that a read marked also holds `drifted_at` and, for an object that does not exist, `gone`; `Refresh` counts a change of either as a change, so the revision moves.

A transaction (`state.Transaction`) holds `id` (`<UTC time>-<6 hex digits>`), `kind` (`plan`, `apply`, `destroy`, `import`, `edit`), `command`, `user`, `host`, times, `status` (`running`, `planned`, `applied`, `rejected`, `failed`), `summary`, the changes with before and after revisions and, for a change that altered the attributes of a record, a `Diff` (`txndiff.go`: `DiffOf`, `Txn.RecordDiff`; the top-level attributes that differ, up to `MaxDiffBytes`, except those that `engine.diffWithhold` (`internal/engine/txndiff.go`) says may hold a secret, which `Diff.Withheld` names; `Store.sealDiffs` moves them into `DiffSealed`, kind `txn-diff`, in a sealed state, and `Store.TxnDiffs` reads either; the signatures do not cover them; `resealSummaries`, `unsealSummaries`, `redactHistory` and `sealedSummaries` treat the box as they treat `SummarySealed`), and the actor, reason, git revision and trace id. `Txn.Start` writes the file with the status `running`, and `Txn.Finish` replaces it; `Finish` writes the file only when the transaction recorded a change or the caller asks for it. A command that is killed leaves the file as it is. `Store.Interrupted` finds the running transactions that no lock which is not stale carries the id of, and `state log` shows them as `interrupted`.

A lock (`state.Lock`) holds the process id, host, user, command, transaction, a per-process nonce, the actor, `since`, `renewed_at`, `kind` (`lock` or `reservation`) and, for a reservation, `expires`. `Store.lock` creates it with `PutIfAbsent` and reads a lock that exists with `readHolder`, which keeps the bytes it read and reads again a lock that cannot be parsed before it takes it for broken, for a filesystem that creates a lock before it writes it. A lock that is stale, or broken, or a reservation of the owner is replaced by deleting it with `deleteLock`, which is a `DeleteIf` on the bytes that were read, and creating it again; a lock that was taken since is another object and is not deleted. `Renew` is a `ReplaceIf` and `Unlock` a `DeleteIf` that check the nonce of the lock they act on, so a command whose lock was reclaimed neither renews nor deletes the lock of the command that reclaimed it; `Unlock` leaves a lock that cannot be read. `Store.Conflict` returns what `Lock` would return and takes nothing. `stale` decides whether another process may reclaim it: a reservation after its expiry; a lock whose process is gone on this host (local backend); any lock not renewed for `state.StaleAfter`. `Locks` sets `Lock.Stale` from it, and `ReleaseStale` deletes the stale locks. `HeartbeatInterval` is 2 minutes and `StaleAfter` 10. `ReserveAll` takes reservations for all addresses or none. The lock on `outputs.json` is taken the same way; an update waits for it for `outputsLockWait`, which is longer than `outputsLockStale`, the time after which the lock of a holder on another host is reclaimed.

`state.Copy` backs `state pull` and `state push`, and copies the `plans` prefix with the records. `tfstate.Convert` backs `state import-tfstate`.

## 4. Providers and the plugin layer

`config` turns each provider struct's `$version`, `$path`, `$protocol`, `$address` and `$from` into a `ProviderReq`. `config.ScanProviders` reads the literal `$version`, `$path`, `$protocol` and `$address` from the syntax of every `.cue` file below the module root, without evaluating, so that `init` can install providers before the specification can load.

`Providers.Resolve` chooses a binary for each requirement, in this order: replay mode; reattach (`$protocol: "tfplugin+reattach"` with `$address`, or `TF_REATTACH_PROVIDERS`); `$path`; the version in `pravo.lock.cue` when it satisfies the constraint; the newest version the source offers for this platform with plugin protocol 5 or 6 (`registry.Client.Resolve`). `FindInstalled` looks in `$PRAVO_HOME/providers`, then `$TF_PLUGIN_CACHE_DIR`, then `~/.terraform.d/plugin-cache`. `Install` downloads the archive, compares its SHA-256 with the source's checksum, unpacks it and returns the hash that `UpdateLock` pins per platform.

A source is `[host/]namespace/type` on a provider registry (default host `registry.opentofu.org`) or `oci://host/path/type` in a container registry, where each version is a tag on an image index with one manifest per platform. `providers copy` writes such a repository.

`Providers.Provider(ctx, key)` starts one process per provider instance on first use and configures it once: `ConfigConvert` converts the provider struct's current value (so provider configuration may reference resources and ephemeral values), then `ValidateProviderConfig` and `Configure`. `Unconfigured` serves function calls. `Close` stops every process it started and only disconnects from a reattached one.

`plugin.Start` launches the binary with go-plugin: the magic cookie handshake, versioned plugins 5 and 6, gRPC only, automatic mTLS. `v5` and `v6` adapt the generated clients in `internal/tfplugin/tfplugin5` and `tfplugin6` to the `plugin.Provider` interface. `plugin.Reattach` connects to a running provider, probing protocol 6 then 5 unless told, and accepts a unix socket or a loopback TCP address. `plugin.Wrap` adds a `Recorder` when `PRAVO_RECORD` names a directory, a replayer when `PRAVO_REPLAY` does, and `Traced` when anything takes spans (`telemetry.Active`). With `PRAVO_TRACES=on`, `engine.startProvider` also gives the provider a `netcap.Capture` (`internal/plugin/netcap`): a forward proxy on the loopback address with an authority made for the run, whose bundle is put in `SSL_CERT_FILE` and the other variables of `Capture.Env`, passed through `plugin.StartWith`. Each request is a `network` span under the newest RPC that `Traced` has running (`AttachCapture`), with the method, host, path without its query, status and sizes and never a header or a body; a host whose client did not trust the authority is tunnelled and shows as `network tunnel`. `PRAVO_TRACES_NET=off` turns it off. `Traced.Close` closes the capture and removes the bundle. The requests that pravo sends itself, to an `s3` or `http` state, go through `netcap.Trace` (`tracedHTTP` in `s3.go`, the HTTP backend's client) and are `network` spans under the `state` span. A recorded response is keyed by method and a digest of the request. The recording directory has mode `0700` and each file `0600`. The stored request keeps the plain fields `name`, `type` and `version` and no configuration, state or private data; the responses are stored as they were returned.

`internal/tfplugin/proto/*.proto` are copies of the protocol definitions. `tools/protogen` produces the message types: `go run ./tools/protogen internal/tfplugin/proto tfplugin6.proto internal/tfplugin/tfplugin6`. The client stubs are written by hand for the RPCs pravo uses.

### 4.1 Discoveries

A discovery lists what exists and manages nothing. `config` finds the structs with `$kind: "discovery"` (`Root.Discoveries`, `config.Discovery`), which are not resources: they are not nodes of the graph and no plan or apply reads them, but they name the provider they list through as a resource does, so the requirement and the instance are found the same way. Its scope is read from the evaluated struct at load, as JSON-ready values; a field without a value is `ScopeErr` and fails that discovery alone. `Discovery.Digest` is the digest of the provider instance, the type, the scope and the limit. The `$ack` list is read as well (`parseAcks`, `config.Ack`) and left out of the digest, so changing it does not make a run stale; an entry with no pattern or with a pattern that matches everything fails the load.

`plugin.Provider.ListResource` calls the server-streaming RPC of protocols 5 and 6 (`ListResource` in the hand-written client of `tfplugin5` and `tfplugin6`), decodes each identity without the identity schema (`decodeIdentity`) and stops the stream at the limit. `schema.ProviderSchema.ListResources` holds the list resource schemas, in the cache and in the pack, and `GenerateCUE` writes them as the catalogue `_#Discovery` and the member `#Discovery` of `#Provider`; `config/prune.go` prunes the catalogue as it prunes the others, and reads a package without it.

`Engine.Discover` converts the scope against the schema of the list resource, asks for one object more than the bound to tell a list that ended from one that was cut, and returns a `state.DiscoveryRun`; the command stores it with `Store.PutDiscovery`. `engine.BuildDiscoveryReport` sets a run against the records, the `$import` declarations and the `$ack` entries of the specification (`discoveryview.go`): an object is managed when a record of the type agrees on every attribute of the identity that it also carries, and on one that is not a scoping attribute; adopting when a resource names it in `$import`; acknowledged when a `config.Ack` covers it by pattern; unmanaged otherwise. `AckEntry` writes an entry that the viewer offers for copying. `AdoptSnippet` and `ReadAdoption` write the resource that adopts an object, naming it in `$import` by its listed identity. An `$import` is a `config.Import` with an `ID` or an `Identity`; `plugin.ImportTarget` carries either to `ImportResourceState`, and `v5` and `v6` ask the provider once for its identity schemas (`GetResourceIdentitySchemas`) to encode an identity (`IdentitySchema.encode`). The report reads and starts nothing, so `pravo discover show` and the viewer both use it. In the state a run is `discovery/runs/<name>.json`; it is not sealed, and `state.Copy` carries it. Nothing else of a discovery is stored: the acknowledgements are code.

The viewer builds `Discovery` (`internal/serve/discovery.go`) for each model from the report, after the secrets of the state are known, and answers `/api/adopt` from the same report. The watcher signs `discovery/` as the component `discovery`.

## 5. Schema generator

`schema.ProviderSchema` holds the provider block, resources, data sources, ephemeral resources and functions as returned by `GetProviderSchema`. Its JSON form is cached at `$PRAVO_HOME/schemas/<source>/<version>.json`; `CacheVersion` invalidates old caches.

`schema.GenerateCUE` writes one package per provider. `session.writeGenerated` places it at `cue.mod/gen/pravo.dev/providers/<namespace>/<type>/<package>_gen.cue` (a non-default host adds a path element before the namespace; `oci/<host>` precedes an OCI source) and writes `cue.mod/gen/pravo.dev/pravo/settings_gen.cue` from `schema.SettingsPackage`. The package exports `#Provider`. `#Resource`, `#Data`, `#Ephemeral` and `#Function` are members of it, which is how a resource built as `$p.#Resource.type & {...}` names its provider. Each definition of a resource, data source, ephemeral resource or function carries `$kind`, `$type` and `$source`; `#Provider` carries `$kind` and `$source`. `$from`, `$import`, `$depends_on` and `$lifecycle` come from constants in `cue.go`. Attribute mapping:

| Provider schema | CUE |
|---|---|
| required attribute | `name: T` |
| optional attribute | `name?: T` |
| computed attribute, optional or not | `name: T \| null` |
| `list`, `set` | `[...T]` |
| `map` | `{[string]: T}` |
| `tuple` | `[T1, T2]` |
| `object`, nested block | a struct, a list of structs or a map of structs by nesting mode; block fields are optional |
| `dynamic` | `_` |

`CUEType` renders types. A field name that is not a plain identifier, or is a CUE keyword, is quoted. When any attribute is named `string`, `number`, `bool`, `int`, `float`, `bytes` or `len`, the file refers to the types as `__string`, `__number` and `__bool`. A package name that is a CUE keyword gets a trailing underscore, and one that starts with a digit gets a `p` prefix. The description becomes a comment; `sensitive`, `deprecated` and `write_only` become `@pravo(...)` attributes.

`init` runs `loadOrGenerate`: when the specification does not load, it scans providers from the imports (`LoadSettingsWith`), generates their packages, and loads again, up to six rounds to find providers that only an imported module needs.

## 6. Modules and the lock file

A shared module is a CUE module. `FindModuleRoot` walks up to the nearest `cue.mod`, so several roots may share one module and its generated packages. Dependencies come from `deps` in `cue.mod/module.cue` through the CUE loader; `ConfigureRegistry` maps `github.com/<owner>` to `ghcr.io/<owner>/cue` when `CUE_REGISTRY` is unset. `pravo mod` runs the embedded `cue mod` commands in the same process.

`pravo.lock.cue` is CUE without a package clause. `engine.Lock` holds `providers` (version, constraints, hashes per platform) and `modules` (version, content hash). `UpdateModules` returns `ErrModuleChanged`, exit 5, when a locked version has different content; `init` relocks.

## 7. Machine interface

`--json` prints one document on standard output and moves text to standard error. `apply` and `destroy` stream `engine.Event` lines (`kind`, `addr`, `phase`, `id`, `elapsed_ms`, `txn`, `trace_id`) and end with a summary line. Errors print as `{"kind":"error","code":N,"message":...}`.

`pravo mcp` reads JSON-RPC from standard input. Each tool in `mcpTools` builds an argument list, and `runSelf` runs the same executable with `--json --no-color`, the actor and reason. The policies are in the state, so the server passes none. `positional` refuses an argument that is empty or starts with `-`.

`internal/telemetry` exports nothing unless `OTEL_*` variables select an exporter (`otlp`, `console`). Apart from that, a recorder span processor keeps the spans of the run and, at shutdown, writes them to `.pravo/traces/<trace id>-<root span id>.json` when the command did some work and `PRAVO_TRACES=on` asked for the record (`PRAVO_TRACE_DIR` moves it, the newest 100 are kept); `internal/serve` reads that directory for the Traces section. While the recorder is the only consumer, `telemetry.TraceID` is empty, so the state and the documents of a command are the same with or without it. A command is a span; `setup …` and `config …` spans (loading, opening the state, providers), `engine plan`, `engine apply` and `engine discover`, the `phase …` stages inside them, `resource <addr>`, `provider <RPC>` and `state <op> <key>` (every request to the state, from `internal/state`'s traced backend) nest under it. Spans and metrics carry addresses, types, actions, counts and outcomes, never values. `TRACEPARENT` continues a caller's trace. `plog` writes the same events to standard error at `-v` (debug) and `-vv` (trace), and attaches them to the active span.

### 7.1 The viewer

`pravo serve` is a web server on the loopback interface and the page it embeds. `serve.New` builds the first model, so that a state that cannot be opened is an error before anything listens; `serve.Listen` binds `127.0.0.1` and nothing else; `Serve` returns when the context of the command ends, which `watchSignals` cancels on `SIGINT` and `SIGTERM`, and closes the event streams first. Closing standard input is not a signal. A sealed state is opened by the command with the identity of the reader, found once before the listener starts (`viewerState` in `cmd/pravo/serve.go`); a record the viewer cannot open is a node with `sealed` set and no attributes, and `Options.Protection` carries no key. The Access view suggests commands as text and runs none.

What it reads: the specification through `config.Load` (a specification that does not load becomes `SpecError`, and the page shows the state alone, with the state location from `config.LoadSettingsWith`), the lock file through `engine.ReadLock`, the state through `Options.OpenState` (`openStateReadOnly`, so a missing state directory is read as an empty one and a write is refused), the provider schemas that are cached under `$PRAVO_HOME/schemas`, the plan file given with `--plan`, decoded by an engine that has the cached schemas and no provider (`LoadPlanFor`, so staleness is judged as `apply` judges it), and the plans stored in the state (`loadStored`, in `stored.go`: `PlanStore.Entries` against `PlanCheckFor`, so a plan stands where the listing of `plan list` puts it, judged by the state alone). `--plan ID` (`Options.PlanID`) lays one of them over the graph from the start, decoded with `LoadPlanUnchecked`; any other is decoded when a request asks for it (`overlayOf`, kept for the revision, with its own copy of the secrets) through `/api/plan`, `plan=ID` on `/api/detail` and `/api/source`, and `plan=none` for no plan. `Node.Plans` and `Node.Overlap` come from the open plans (`markNodes`). It takes no claim on a stored plan, marks no progress and collects none. What it never does: write a record, a transaction, a lock, `pravo.lock.cue` or a generated package; start a provider; download a provider, a schema or a CUE module (`uncachedModule` looks in the CUE cache before the load); take the lock of a record.

The model is built once for each revision. The watcher samples, every second, the attributes of the specification's files and of the `*.cue` files of the directory, of the plan file, of the state (the directories `resources`, `txn` and `locks`, which the local backend changes with every write; for a bucket, a listing every five polls) and of the stored plans (the directory `plans`, by name, size and time of its entries; for a bucket, a listing of `plans/` and a digest of each progress object, since a replaced object keeps its key). A plan that is not applied expires without a write, so `setPlanExpiry` gives the watcher the nearest expiry of the open plans, and passing it moves the signature once. The revision is a digest of the five signatures `state`, `spec`, `plan`, `locks` and `plans`. A request that finds the model older than the revision builds a new one, keeping the loaded specification if its files did not change, and `/api/events` sends `change` with the new revision and the components that moved. A value that the schema does not mark but that contains a sensitive string of the state is withheld as well, since a file built from a password has no flag of its own.

Security model. The listener is on `127.0.0.1` or `::1`, and `Serve` refuses a listener on any other address. Each run makes a 128-bit token, printed in the address; `GET /?token=` sets a `HttpOnly`, `SameSite=Strict` cookie named for the port and redirects to `/`, and the API accepts that cookie or `Authorization: Bearer`, compared in constant time, and nothing in a query. A request whose `Host` is not a loopback name with the listening port is answered with 421, a `Sec-Fetch-Site` of `cross-site` with 403 (`same-site` too, for the API), and no CORS header is sent, so a page of another origin neither reaches nor reads the API. Values are redacted on the server by the schema, by the name of the attribute, for a type without a schema and for derived text (a stored plan by the same code as a plan file, with the secrets of its own values), and the private blob, the configuration digest and the provider configuration of a record are never sent. Source lines come from the files `Root.Sources` lists, selected by the address of a node and never by a path, with literals assigned to sensitive attributes masked, and the page is served with a content security policy that allows its own scripts and styles only.

### The library

`pravo/pravo` is the public package: `pravo.Open` returns a `Workspace` with the operations of the commands (plan, apply, stored plans, drift, why, discover, state queries). Only `cmd/pravo` reads flags and environment variables, prints, and prompts; the package takes an `Env`, a progress callback, a log handler (`SetLogHandler`) and the policy for opening a sealed state (`Config.OpenState`) as arguments. Workspaces on different directories run in one process, and nothing changes the working directory. `pravo mcp` serves `pravo_state_query` and `pravo_dependents` through the library; its other tools run the binary as a subprocess, which keeps process-wide state (working directory, environment, telemetry) out of the server. `examples/embed` uses nothing but the public package.

Compatibility: the package is v0 and unstable. Its types that alias internal ones (`Root`, `Store`, `Engine`, `Plan` and the like) will be replaced by types of the package. A change to the package is allowed to break callers in this repository's own module until it is declared stable; the `cmd/pravo` tests and `examples/embed` are the callers that must keep building. The JSON that the commands print is the stable surface.

## 10. How the documentation is verified

Every command shown on a page is a `run` block that `capture` executes with the real binary; the output beside it is an `out` block that `capture` compares. A page passes when nothing differs.

|---|---|
| `go run ./tools/capture -check ./docs` | Every page: commands, exit codes, output. `-update` rewrites `out` blocks from a run. |
| `go run ./tools/sitegen -pravo-bin <binary>` | Front matter, containers, code attributes, links between pages, banned phrases in `docs/`, `site/` and `README.md`, landing partials and data tokens, then every link and fragment of the output. Takes the version line from the binary. |
