What providers can already do

A provider is the small program that knows one cloud. Some providers can already say what exists in an account. This chapter explains what they can say, which ones can, what OpenTofu and Terraform do with it, and what pravo does when a provider stays silent.

  • 9 minute read

  • Facts as of 22 October 2026

Each room has a caretaker who knows where things are

Think of the toy room again. It is shared by many children. Each room has one caretaker. The caretaker knows how to fetch a toy, put a toy away and change a label.

pravo never walks into the room itself. It asks the caretaker. In the cloud the caretaker is called a provider. There is one for aws, one for Kubernetes, one for each service that has made one.

pravo and the provider talk down a fixed phone line, the plugin protocol. OpenTofu and Terraform use the same line. So pravo can use the same caretakers without changing them.

Explain it like I am five

You ask the caretaker, "What is in the room?" Some caretakers can answer. They read out every toy, one by one. Other caretakers only know about a toy when you point at it and say its serial number.

Three tricks matter for brownfield, and providers are learning them

For this design three things a provider can do are useful. Each has a plain meaning and a technical name. The technical names are the real calls in the protocol files pravo already carries.

  • List

    "Tell me everything in the room." The provider reads out each thing it finds, one after another, as a stream.

    Technical name: ListResource, with ValidateListResourceConfig to check the question first.

  • Identity

    "Show me the serial number." The exact key that says which toy this is, even if someone renames it.

    Technical name: GetResourceIdentitySchemas and UpgradeResourceIdentity.

  • Draft the label

    "Write me a first draft of the label for this toy." A draft only. A person or pravo still checks it.

    Technical name: GenerateResourceConfig.

Think of it like

A name on the box and a serial number on the bottom

Children rename toys all the time. "Rocket" becomes "Big rocket". The serial number on the bottom never changes. A good list gives you both: the name to read, and the number to rely on.

the display name, for people

For engineers: where the three tricks sit in the protocol

All three are in the protocol files pravo vendors, versions 5.11 and 6.11 (file read: internal/tfplugin/proto/tfplugin5.proto and tfplugin6.proto). The two protocols carry the same calls for these features. Only some names differ, for example protocol 5 calls the schema call GetSchema.

  • The request names a list type, a provider-defined config, whether to include the full object, and a limit.
  • Each event in the stream carries an identity, a display_name, optionally a resource_object, and diagnostics.
  • There is no capability bit for list or identity. A client finds out by asking GetMetadata (list_resources) and GetProviderSchema (list_resource_schemas), and must accept the gRPC answer Unimplemented. Only generate_resource_config has a bit in ServerCapabilities.
  • The label "6.10" names three different file contents across Terraform tags, so pravo detects features and never versions.

Sources: proto files read in the pravo repository; Terraform tags v1.11.0 to v1.17.0 fetched from hashicorp/terraform (research note 1, section 6.1). Verified.

What happens when pravo asks for a list

The sequence is short. Step through it. The order is the natural composition of the calls in the protocol. No one has watched a whole run end to end, and the last page of this chapter says so.

  1. Ask what it can list

    pravo asks the provider which kinds of thing it can list. A provider that cannot list gives an empty answer or says "not implemented". pravo accepts both.

  2. Say where to look

    pravo configures the provider for one account and one region. This must work before any list call. The one test we ran skipped this and the provider stopped.

  3. Read the stream

    The provider sends one name tag and serial number at a time. It sends no total and no "that was the last one". The stream ends.

  4. Write down the facts

    pravo stores identity and display name. It stores no attribute values, because a listed thing can carry secrets.

For engineers: the call order, and what is in the way
  1. GetMetadata (may answer Unimplemented), GetProviderSchema, GetResourceIdentitySchemas (may answer Unimplemented), and the generate_resource_config capability bit.
  2. ConfigureProvider for the account and region. It must succeed before any list call.
  3. ValidateListResourceConfig, which is optional and cheap.
  4. ListResource. Read events until the stream ends. A broken stream (gRPC Unavailable) is a failure and never "no results".
  5. To adopt one object later: ImportResourceState then ReadResource, in memory.

The list-capable provider on this machine, aws 6.69.1, speaks protocol 5. So pravo has to add list support to both its protocol 5 and protocol 6 adapters, or the first real provider finds nothing. Today pravo's hand-written client carries 17 unary calls and no streaming call, and its Provider interface has no list, identity, metadata or generate-config method.

Sources: research note 1, sections 3, 4.4 and 5; code read in internal/tfplugin/tfplugin{5,6}/client.go and internal/plugin/provider.go. Verified by reading. The call order itself is the natural composition of the messages and was not watched in a run.

A list answer is a name tag and a serial number, nothing more

This is the most important limit. Say a caretaker reads out the room. You learn the name of each toy and its serial number. You do not learn its colour, its owner, its price or which box it belongs in.

What an answer carries

  • An identity, the serial number.
  • A display name, the name for people.
  • Optionally the full object, if asked. That can cost one extra call per object.
  • Warnings or errors for that one item.

What it does not carry

  • A page number, a total, or a "that was the last one".
  • A "changed since" marker. Every look is a full look.
  • Tags, owner, or who created it.
  • A parent link. A parent is only a required setting in the list question.
  • Any promise about order, cost or speed.

Source: the proto files read field by field (research note 1, section 2.2; DESIGN.md evidence rows 1 and 2). verified How aws orders results and whether the display name is always set are unverified.

Where this gets messyimpractical

Listing is not the same as "everything that exists"

What goes wrong
The aws provider's own contributor documentation says its list leaves out things by design: objects that cannot be managed (default database parameter groups), special cases (the default network and its parts have their own list types), machines owned by an Auto Scaling group, and machines that are terminated or shutting down. It also lists one region per call.
So we propose
Never say "everything". pravo shows a coverage word for each type and says once per provider what the provider leaves out. A missing item means "unknown", not "does not exist". There is no "percent managed" figure, because nobody knows the total.

Source: aws provider contributor docs on list resources, and its instance list page, fetched (research note 2, section c; DESIGN.md evidence row 21). verified

"OpenTofu has no list support" is true only for what we read

What we checked
We read three OpenTofu v1.13.2 source files. They handle identity and contain no list or generate-config code. The issue asking for it was open on 20 October 2026. We did not search the rest of the repository, and an RFC may exist somewhere we did not look.
So we propose
Say "not found as of 22 October 2026" and ask anyone who plans to wait for OpenTofu to look again. The provider-side calls are the same under either tool, so pravo's design does not depend on the answer.

In plain words

The caretakers have learned to read out the room. The two big tools have not all started asking. pravo can ask them itself.

In the same issue, one participant (listed in the research as a contributor, so this is not a maintainers' position) asked whether anyone has tried agents for import, because writing code one object at a time cannot see how a whole estate should be arranged. Another said OpenTofu may diverge from Terraform's design. That matches the plan here: pravo does the mechanical part deterministically, and an agent can help with the arrangement, but nothing needs one.

When a provider cannot list, pravo falls back, and says so

Most types cannot be listed today. A caretaker who cannot read out the room can still pick up a toy if you hand over its serial number. So the design has a ladder. The first rung finds things. The other rungs let you adopt things you already know about.

  1. Ask the provider to list

    Works for the types the provider can list: 253 of 1,735 in aws 6.69.1. pravo finds things you had not heard of.

    discovers: yes | needs: a list-capable provider

  2. Bring a file of ids

    A file, one line per object, with the type and its id or identity. It can come from the cloud's own command line tool, from kubectl, or from an agent that did the research. pravo adopts what is on the list.

    discovers: no, it only adopts what you bring | works for any type that can be imported

  3. Type one id

    pravo adopt TYPE ID for a thing you can already name.

    discovers: no | works for any type that can be imported

  4. Use a recipe

    The design proposes a folder of recipes for thirty aws types chosen from those that cannot list (the thirty are not picked). A recipe is a short shell command that prints the file of ids and notes how that type spells its id.

    unverified: nobody has written one yet, and recipes can only be tested against a sandbox account

  5. Ask a person or an agent

    For the rest, a person or an agent finds the objects and the id format, then writes the file. Once the file exists the rest is the same deterministic path.

    the realistic helper at scale, and the one step that needs outside tools

Where this gets messyimpractical

For types that cannot list, nothing in pravo discovers anything

What goes wrong
About 1,450 of aws's 1,735 types (after the thirty recipes) and every Kubernetes type have no list. The protocol has nothing to offer there. The manual path is complete from the id onward, and thin before it. At a thousand objects across thirty such types, producing the list by hand is not manageable.
So we propose
Say it plainly and do not build adapters for each cloud's inventory service. We rejected those because each needs a table that maps the cloud's ids to provider types, and nobody publishes one except for Azure. The file door lets other tools feed pravo.
Where this gets messyimpossible

Providers built only on the older plugin kit cannot list at all

What goes wrong
The plugin kit most older providers use (terraform-plugin-sdk, "SDKv2") answers the list call with an error from version 2.38.0 on. Such a provider will never list. The aws provider lists anyway, apparently through its newer framework layer (inferred, unverified in its source).
So we propose
Treat the error as "this type cannot list", show the coverage word no-list, and move to the next rung.

Sources: terraform-plugin-sdk v2.38.0 release notes and the framework changelogs, fetched (research notes 1 and 2; DESIGN.md evidence row 20). verified
