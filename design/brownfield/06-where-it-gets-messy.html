Where it gets messy

Some of this design cannot be built. Some depends on other people's software. Some cannot be made safe. Some is too much for a person to do by hand. This page says which is which, and why.

  • 15 minute read
  • Pushback is a feature
  • Every claim is marked verified or unverified

The tidy-up crew has limits, and you should hear them first

Back in the toy room, the crew promised to walk round and write down every toy on the floor. Here is what it cannot promise.

Some toys sit in a locked cupboard and the crew has no key. Some toys look like yours but belong to the neighbour, and the crew cannot always tell. A toy might be written on the list twice by two different children, and then putting one away takes the other with it. And if a thousand toys are on the floor, a person cannot label them all in one afternoon.

Think of it like

Four kinds of "not quite"

A locked cupboard
A resource type the provider cannot list
A neighbour's toy
An object another team, tool or controller owns
One toy, two labels
Two records that own one real object
A thousand toys, one afternoon
Batches, pull requests, calendar time

In plain words

The design is honest about the places where it stops, and so is this page.

Five kinds of trouble

Each card below carries a severity tag. impossible means the thing cannot be done, or cannot be made safe, whatever we build. impractical means it can be done and is not worth its cost or does not scale. uncertain means nobody has checked.

What we will not build, and why

Explain it like I am five

These are the things the crew will not do even if you ask nicely, because each one would hurt someone's toys.

We will not build thisimpossible to make safe

Shadow records inside the managed state

What goes wrong
A probe in the study showed that a record with no declaration is planned for deletion (dice will be destroyed, where dice is a sample resource used in the probe). destroy destroys every record. Ten more code paths walk all records. One missed path deletes a real object.
So we propose
The shadow estate lives in a separate ledger prefix and is never a record. This is the most dangerous option we rejected, and the reason for design decision A.
We will not build thisimpossible

A promise of the complete estate, or a "percent managed" figure

What goes wrong
Providers leave objects out of lists on purpose, some types cannot list at all, and nobody can count what they cannot see. The denominator is unknowable. A high percentage on a vendor page is a marketing figure, not a measurement.
So we propose
A coverage word per type. Absence from the ledger means "unknown", never "does not exist".
We will not build thisimpossible

Discovery for types that cannot list

What goes wrong
The protocol has nothing to offer for them. In aws 6.69.1 that is about 1,450 of 1,735 managed types once the thirty recipes are subtracted, and every type in the cached kubernetes provider. A file of ids and a typed id are adoption inputs, not discovery.
So we propose
Say it plainly. Ship recipes for thirty aws types chosen from those that cannot list (not yet picked, none written). For the rest, you, another tool or an agent brings the list. This is the largest honest gap in the "works without an agent" promise: the manual path is complete from the id onward, and thin before it.
We will not build thisimpossible

A promise that an empty plan means "described"

What goes wrong
An attribute the CUE leaves null is inherited from the prior value, so an empty plan says nothing about it. A generator that wrote almost nothing would pass.
So we propose
An empty plan is worded as "not contradicted". The default profile writes the optional-and-computed attributes, and the gate prints specified N, inherited M and warns when M exceeds N.
We will not build thisimpossible

Incremental sweeps and a watch daemon

What goes wrong
The list call has no "changed since", no pagination token and no total. Every sweep is a full scan of its shard.
So we propose
Cron or CI runs sweep --due. pravo has no daemon.
We will not build thisimpractical

Auto-adoption, or an agent or cron job that merges

What goes wrong
Adopting makes a real object destroyable, by design. Ignore rules are the only way to make shadow objects vanish from view. Both decisions need a human.
So we propose
A batch needs a human merge, always. An agent drafts, the gate checks, a person merges.
We will not build thisimpractical

Native cloud-inventory adapters

What goes wrong
Cloud Control, Resource Explorer, Cloud Asset Inventory and Resource Graph each need a table that maps a cloud id to a provider type and an identity. Nobody publishes one, except aztft for Azure.
So we propose
The file door lets other tools feed pravo, without pravo owning a mapping table for every cloud.
We will not build thisuncertain

A dependency on tofu query or terraform query

What we checked
No tofu query was found in OpenTofu v1.13.2 (three Go files read, the rest of the repository not searched). The OpenTofu issue about it (#3787) was open and labelled pending-decision on 20 October 2026. Terraform shipped terraform query in 1.14.0. That is not a claim about anywhere else.
So we propose
pravo talks to providers directly, so the same calls serve either tool and pravo waits for neither. A reader deciding whether to wait for OpenTofu should check the issue again first.
We will not build thisimpractical

Observe-only records and a rights ladder, in the first version

What goes wrong
An observe, update, delete ladder (as other tools offer) needs new record semantics, a much larger change.
So we propose
prevent_destroy plus the protected-record mark (decision D2) gives most of the safety. A watch-only recipe could be documented. Whether ignore_changes: "*" covers nested blocks is unverified, so the generator never emits it.
We will not build thisimpractical

Tag triage at sweep time, writing tags, cleaning up the shadow estate

What goes wrong
A sweep holds identity and a name, no attributes, so it has no tags to triage on. Writing tags would end the promise that discovery only reads. Deleting what nobody owns is a different product.
So we propose
A controller-marker check at adopt time, when the object is in memory anyway. Nothing else.
We will not build thisimpractical

Automatic modules or for_each

What goes wrong
Object-by-object generation cannot see the architecture. No tool in the study does this well, and one participant in the issue above (listed as a contributor in the research) asked a question that points the same way.
So we propose
Generate flat, once. Folding twins into loops and modules is human or agent work afterwards, moved with $from and proven by the same empty-plan gate.
We will not build thisimpractical

Plan-as-oracle minimisation, stored attributes, SQL over the ledger

What goes wrong
Dropping attributes while the plan stays empty multiplies provider calls. Storing attributes puts secrets in the ledger.
So we propose
Start small by omitting computed attributes, pin only what the plan shows, keep the ledger to identity and name.

What depends on providers, and what nobody has checked

Explain it like I am five

The crew can only read out names for the kinds of toy its helper knows how to list, and so far we have never watched the helper finish a list.

Depends on providersimpractical

Coverage is partial and uneven

What goes wrong
Besides the figures above: aws 5.100.0 has no list and does not implement the identity call. By documentation page count, which is only a proxy, azurerm lists about 11 percent, google about 13 and awscc about 75. None was found for github, datadog, cloudflare, vault or helm.
So we propose
Compute the coverage table from the installed provider version. Never hard-code it. The oldest aws changelog mention of list is 6.14.0 (18 September 2025), so coverage moves quickly.
Depends on providersimpossible

Providers built only on the older SDK cannot list

What goes wrong
terraform-plugin-sdk 2.38.0 answers the list call with an error, so a provider built only on it has no listing, however good the protocol is.
So we propose
The file and typed-id doors, which work for any type that imports.
Depends on providersimpractical

Kubernetes users are on the file door only

What goes wrong
The cached provider lists nothing. Whether a list would add much is an assumption we have not tested; objects made by operators, Helm or hand are exactly the ones nobody has in YAML.
So we propose
Turn kubectl get -o json into JSON lines. kubernetes_manifest has an identity. We claim nothing more.
Depends on providersimpractical

A list is best effort, never complete

What goes wrong
In aws the list excludes non-manageable objects (default RDS parameter groups), special cases such as the default VPC, instances owned by an Auto Scaling group, and instances that are terminated or shutting down.
So we propose
Treat "complete" as the union of list, file and typed id, never one call. shadow prints the standing note once per provider.
Depends on providersuncertain

A listed object may not equal what Read returns

What goes wrong
One third party reports zero values that break conflict rules, failures on single types, and no references between listed objects. It is a single source and unverified.
So we propose
Assume all three. A sweep never asks for the full object. Adopt always imports then reads, validates, fails per shard without stopping the sweep, and recovers references by heuristic.
Depends on providersuncertain

Identity import and import ids

What goes wrong
Whether aws honours an import by identity alone is unverified. The import id format for each type is not in the protocol. A single required identity attribute as the id is a heuristic that is unverified for composite and ARN ids.
So we propose
The typed-id door always stays open. Phase 0 tests identity import on a real account.
Depends on providersuncertain

Providers can crash, and a list is not a snapshot

What goes wrong
An unconfigured list call killed the aws provider process (cause unverified). Cloud list APIs are often eventually consistent, though no cloud statement was verified in the study. A provider may also end a stream with success after an error diagnostic (inferred, never observed).
So we propose
Supervise and restart the provider process. Treat the ledger as a hint and re-read the real object at adopt. An error diagnostic anywhere makes the attempt incomplete, so nothing is marked unlisted wrongly.
Depends on providersuncertain

Nobody has measured time, rate limits or billing

What goes wrong
The figure of up to 4,301 list calls across, for example, 17 regions (an illustrative number) is arithmetic. The cost of 8,000 to 12,000 provider calls to adopt a thousand objects is arithmetic too.
So we propose
A spike on a read-only sandbox aws account (decision D7) measures roughly twenty of these unknowns before anything is built on them.

What cannot be made safe, only safer

Explain it like I am five

Some risks stay even with good locks, so we say where they are, put guards round them and tell you to check.

Cannot be made safeimpossible

Adoption makes an object destroyable, on purpose

What goes wrong
Once an object is managed, removing its text plans the deletion of the real object. prevent_destroy does not cover that case. Today a record without a declaration is planned for deletion.
So we propose
Copy the protection into the record, so a protected record that is no longer declared makes the plan an error (decision D2). If an older pravo binary can drop that field, protection can vanish silently, and then a format bump is the price (D5, unverified). Protection, policy and review reduce the risk. No tool removes it.
Cannot be made safeimpossible

Two records for one object

What goes wrong
Destroying either record destroys the other's object. Locks are per address, so two addresses with one import id both import. The identity lock (decision D13) stops it inside one root, and only when the identity is known. An id-only key can miss an object reached once by identity and once by a differently formatted id.
So we propose
A plan-time check, the identity lock, known states and review. Across roots nothing detects it; a shared ledger (D4) would, and it is not built.
Cannot be made safeimpossible

Ownership cannot be detected in general

What goes wrong
Objects owned by CloudFormation, operators, service-linked roles or another root are recognised at best by naming or a marker. The list protocol does not say who created an object. One vendor claims it can; the method is unpublished.
So we propose
Ignore rules with a reason, known states with an age, and a controller-marker check at adopt time. The marker tag names were not verified and must come from the aws documentation before they are coded (decision D14).
Cannot be made safeimpossible

Secrets the API never returns, and secrets nobody marked

What goes wrong
A required password cannot be read back, so a human must supply it. Provider sensitive flags are incomplete: a password in user_data or a tag is not marked. Our own detector is best effort.
So we propose
Holes for required secrets, a detector, no values in the ledger, redacted tool output by default, and a secret scanner on every pull request. "An agent never sees a secret" would be false. The true claim is that it never chooses one and sees values only if an operator allows it.
Cannot be made safeimpossible

Equivalence and granularity are human questions

What goes wrong
An empty plan means the CUE reproduces what the provider reads, defaults included. Whether those defaults are intended is for the owner. Likewise, whether a subnet is an inline block or a separate resource, or how to model association objects, is the owner's preference and the tool cannot know it.
So we propose
Report every frozen default and pin. Report granularity per type in the review output. The choice stays human.
Cannot be made safe yetuncertain

Identity keys are canonical only as far as a real list event fills them

What goes wrong
Nobody has seen a real list event. The ledger key is built from required identity attributes plus the scope's account label. If a real event fills fields differently from a read, matching fails.
So we propose
Phase 0 checks what a real list event puts in account_id and region, and whether the read call's new identity gives the same key. Until then the key is a design under test.
Cannot be made safe yetuncertain

The safe checks themselves are assumptions

What goes wrong
That a scratch overlay of the state is cheap to build, that ignore_changes behaves as hoped, that an older binary keeps an unknown record field: all are unverified.
So we propose
Phase 0 checks about ten questions about pravo itself before any of them is relied on.

What is impractical for a person at scale

Explain it like I am five

Putting away ten toys is a nice afternoon, and putting away a thousand is a month of afternoons.

Does not scale by handimpractical

A thousand objects are twenty pull requests, one after another

What goes wrong
A later batch can link to an earlier one only once the earlier one is applied. Each batch has a plan, an apply and a second plan. That is days of calendar time.
So we propose
Say so. Order batches by dependency (--order) and re-link afterwards (--relink). One gate over several pending batches might shorten it; that is unverified.
Does not scale by handimpractical

Making the id list for many types that cannot list

What goes wrong
At a thousand objects across thirty such types, this step is not manageable by hand. The recipes need the vendor command-line tool and credentials. They cannot be tested in pravo's documentation build, which has no cloud account. Nobody has written one yet.
So we propose
Recipes for thirty aws types, tested against a sandbox account. Beyond them, an agent is the realistic helper, and its output is a file that is deterministic once written.
Does not scale by handimpractical

Reading every object

What goes wrong
Nobody reads a thousand generated files with care.
So we propose
Review by rule and by batch: the shadow table, the ignore rules, the batch summary, the links and pins, and a sample of the CUE. The gate makes the unread part safe. It does not make it well named.
Does not scaleimpractical

Thousands of records in one root

What goes wrong
After adopting N objects every command reads N more records, 8 at a time on a local store and 64 at a time on S3.
So we propose
Split roots by account or region before adopting thousands. Cost follows the scope you declare, not the change.
Does not scale by handimpractical

Reference recovery is a heuristic

What goes wrong
The protocol does not say which attribute points at which type. A subnet adopted before its network keeps a literal id and gets no dependency edge: no ordering, no blast radius.
So we propose
Replace a string only on an exact, unique match with a reference-looking name. Print every substitution in a links table. Re-link afterwards. The type-order table is data and incomplete by nature.

What is messy in pravo today

Explain it like I am five

Before the crew starts, we have to fix a few loose floorboards in the room itself.

"Phase 1 needs nothing outside pravo" is true and misleading. It needs core changes, and three of them touch a property pravo documents today. The roadmap puts them first.
