Four rules for a careful tidier

Go back to the shared toy room. A tidier called pravo arrives. A careful tidier follows four rules. The whole design is these four rules, written down. They are a closer look at the five verbs on the front page: look and write down are rules 1 and 2, decide is rule 3, adopt and prove are rule 4.

  • 1. Look before you touch

    Ask the caretaker (the provider) to read out what is on the floor. Pick nothing up.

  • 2. Write down what you saw

    Keep a notebook (the found list, called the ledger). It is facts only, and it can be thrown away and rebuilt.

  • 3. A person says "ours"

    The helper never decides alone. The decision is written in a text file with a reason.

  • 4. Prove the label first

    Hold the label up against the toy. Tape it on only if nothing would change.

Explain it like I am five

pravo is the tidier. The provider is the caretaker who knows the room. The cloud is the room. A resource is a toy. The notebook (the found list) says what is on the floor. The state is the list on the wall. "Adopting" a toy means: pick it up, label it, put it in a box, and add it to the wall list.

The life of one toy

Press Play, or click a step. The left side is the toy room. The right side is what pravo writes down. Follow the blue car. The drum is the neighbour's.

The blue car could be a storage bucket called legacy-logs-2019. The drum could be a resource that belongs to another team.

  1. On the floor

    The blue car is real. Nobody wrote it down. pravo does not know it is there, so pravo cannot hurt it. In the cloud: an object that no record in pravo's state owns.

  2. Seen

    seen pravo asks the provider (the caretaker) to read out the floor and writes the names in its notebook, the found list. This is a sweep. pravo asks only for names and ids and keeps only those.

  3. Decided

    elsewhere You read the list. The drum is on the neighbour's list, so it is marked elsewhere and left alone. (A toy that is ours but rubbish for now would be ignored, with a reason you write down.) The car is left for you to pick. This step covers ignored, elsewhere and the choice to adopt.

  4. Declared

    declared You say: adopt the car. pravo reads it in memory, drafts the label as CUE, and tests the draft against a scratch copy of the room (assumed feasible; the first spike checks it). Only a draft that passes is written to a file.

  5. Proved

    pravo makes a plan and saves it. The plan must say 0 to add, 0 to change, 0 to destroy. A policy we would write (not written yet; whether the policy language can say this is unchecked) refuses any other plan. An empty plan is the proof.

  6. Managed

    managed You apply the saved plan. pravo writes one record and the car is in its box. A second plan must say "no changes". From now on, pravo takes charge of it.

In plain words

The toy never moves until a person says so, and the label has to pass a test first.

The golden rule: nothing, ever, unless claimed

pravo may do exactly two things to a toy it was not given: look at its name, and read it when you ask to adopt it. It never changes it, tags it, plans a change for it or deletes it.

A toy is "given" in exactly one way: you adopt it, the plan is reviewed and you apply it. Looking round does not give anything. Ignoring does not give anything. A sweep does not give anything.

Explain it like I am five

The tidier is allowed to look at any toy. It is only allowed to touch a toy after you hand it over. Floor toys are on a different shelf from the boxed ones, so the tidier cannot grab one by mistake.

For engineers: why the found list is not a record

A shadow object is never a record in resources/. A probe found that a record with no matching declaration is planned for deletion (dice will be destroyed, action delete), and that destroy deletes every record. Ten more code sites walk all records. One missed site would delete a real object.

So the ledger lives under inventory/, a sibling of resources/. Store.load never touches it. The build must pass one test: with 10,000 ledger entries and no records, plan, apply and destroy read none of them and propose no change.

Source: DESIGN.md sections 4 and 5, evidence rows 33, 34 and 37 (probes and code reads in the pravo repository).

Where this gets messyuncertain

"Read only" is a habit of providers, not a rule of the protocol

What goes wrong
The listing call and the import call are read calls by convention. The plugin protocol does not forbid a provider from doing more, and nobody read a provider's list or import code in this research. pravo itself writes nothing to the cloud, but it cannot prove what a provider does.
So we propose
A second fence: sweeps run with a dedicated read-only cloud role. That role, not pravo, is the real guarantee.
Where this gets messyimpractical

Adopting makes a toy deletable, on purpose

What goes wrong
Once a toy is managed, removing its text from the specification plans its deletion. That is how pravo works today, and no tool can make it safe for every case.
So we propose
Adopted records are protected, and a protected record whose text is gone makes the plan an error, not a delete. That changes a documented property of pravo, so it is an open decision. See the decisions page.

"Prove it with an empty plan"

Before pravo tapes a label on a toy, it holds the label up against the toy. If they match, nothing needs to change. In pravo words: the plan is empty.

An empty plan reads 0 to add, 0 to change, 0 to destroy. It is the success test for the whole design.

Explain it like I am five

You draw a picture of your toy. You hold the picture next to the toy. If the picture is right, nothing needs fixing. If the picture is wrong, you would need to change the toy to match it, and we do not want that.

The test is run twice, on purpose

  1. The gate, before anything is saved

    pravo makes the label, then plans it inside a scratch copy of the room. If the plan is not empty, nothing is written. The gate is advisory, because the toy may change before you apply.

  2. The proof, after the apply

    The saved plan is applied. Then a new plan must reach zero resources. This one is the authority.

What an empty plan does not prove

This is the honest part. An empty plan says only that your label does not contradict the toy. It does not say your label describes the toy.

If a setting is left blank in the CUE, the plan inherits the toy's current value. A blank picture matches everything. A plan can be empty because the CUE says very little.

One toy, by hand. You choose the bucket, run one command, read the report, plan, apply and plan again.

An agent runs the same commands through pravo's read-only tools and proposes the choices. It sees values only if the operator allows it. You still read the report and merge.

  • It may read the found list and propose ignore rules, each with a reason.
  • It may print a redacted proposal of the label, and explain why a gate said "differs".
  • It may suggest where a secret should come from. It never chooses the secret.

In plain words

The agent is a fast helper, not a different road. The check at the end is the same for a person and for an agent.

For engineers: what the gate checks and what it freezes

The generator writes optional-and-computed attributes it can read (--spec full, the default), so an S3 bucket's bucket and region are in the CUE and a later change to them shows up as a diff. The cost is that a value the provider defaulted is frozen as if the owner chose it. The report lists every pinned and every frozen attribute.

The protocol cannot tell a default from a choice. A --spec minimal result is labelled "tracked, not specified", a way to put an object under the engine and not a description of it.

Adoption always ends with an apply, even when the plan changes nothing, because an adopted record has no dependency edges or config hash until an apply writes them. Source: DESIGN.md sections 2 and 7 (steps 3 to 9); the dependency-edges fact is evidence row 38, from a probe.

What the idea cannot promise

Two limits belong next to the idea, not hidden at the back.

Where this gets messyimpractical

Most toys cannot be found by walking the floor

What goes wrong
A provider can list only some types. In the installed aws provider that is 253 of 1,735 managed types. The cached Kubernetes provider lists none. For the rest, pravo discovers nothing: you bring the ids.
So we propose
Adoption by id comes first and works for any type. Listing is an accelerator for the minority that supports it.
Where this gets messyuncertain

The first release changes pravo's core

In toy-room words: before the tidier starts, three loose floorboards must be fixed, and each changes a promise pravo makes today.

What goes wrong
Import must stop writing state at plan time, an adopted record must be protected against the delete that follows removing its text, and two records must never own one object. Each touches something pravo documents today.
So we propose
Treat these as the first work, and decide them before building the rest. They are decisions D1, D2 and D13 on the decisions page.
