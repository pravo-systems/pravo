Chapter 3 of 7

A worked example

One small company, four things somebody made by hand and one that is not theirs, and the road from "nobody knows" to "the plan is empty". First in pictures. Then with the real commands, once by hand and once with an agent helping.

  • 12 minute read
  • Commands are proposed; nothing here has been run

Lantern and Company has four things nobody wrote down

Lantern and Company sells hand-made lanterns online. Three years ago Ana set up its cloud by clicking in a web page. She made a bucket for product photos, a virtual machine for orders and a database for the shop. A virtual machine is a computer that lives in the cloud. A bucket is a folder in the cloud. A database is where the shop keeps its facts.

Now Ben has joined. He wants all of it under pravo's control. Today pravo knows about one bucket, the site assets, which Ben made last month with pravo. It knows nothing about the four things Ana's team made by clicking: the photos bucket, the orders machine, the shop database and a scratch bucket for a weekly export. And there is a sixth thing in the account that belongs to the platform team: its logs bucket. Six things in all, one of them already managed.

This is a brownfield project. Here is the room.

Explain it like I am five

Ben wants to tidy the toy room. He cannot tidy what he cannot see. So first he walks round and writes down every toy on the floor. Then he decides what is his, what is the neighbour's, and what is rubbish. Then he labels his toys and puts them on the list.

The whole story in six pictures

Step through it. Each picture changes one thing. The five things not yet on the list change colour as pravo learns about them. The sixth, the site assets bucket, is already managed and stays in its box.

  1. Nobody has a list

    The room is full, and nothing is written down. pravo knows about the site assets bucket and nothing else.

  2. Walk round and write it down

    pravo asks the provider to read out what exists. Six things come back, one of them already managed. The other five are marked seen. Nothing is touched.

  3. Decide what is whose

    The scratch bucket is rubbish for now: ignored, with a reason. The platform logs bucket is on the neighbour's list, so it is marked elsewhere and left alone. Three remain.

  4. Pick up and label

    Ben asks pravo to adopt the three. pravo writes a label for each, checks it against the real thing, and marks them declared.

  5. Check the list matches

    The plan says there is nothing to change. The three are managed.

  6. Walk round again, later

    A night job looks again and says if anything new has appeared on the floor. The ignored things stay ignored.

In plain words

Look first. Write down what you find. Decide. Only then change anything. And at the end, check.

The same story with real commands

Now the engineer's version. Every step has two tabs. Manual path is complete once you have a list of ids: you type each command yourself. (What the sweep finds depends on the live cloud, so two sweeps can differ; the check that follows is the same each time.) With an agent shows the same step with an agent helping. The agent runs the same tools and proposes. A person still merges.

In plain words

The agent is a fast helper, not a different road. Everything it does, you could type.

The commands sweep, shadow and adopt are proposals and do not exist yet. Output is illustrative, adapted from the design document (section 8). Names are made up for this company. The tabs remember your choice across the site.

Step 1

Say where to look

Decisions live in your CUE files, where they are reviewed like code. A scope names the account, the kinds of thing to look for, and two logins: a read-only one for looking and the normal one pravo will use after adopting.

The plan costs nothing. It counts the list calls and touches nothing.

The agent reads what each type can be asked (pravo schema --list TYPE, through the pravo_schema tool). It drafts the same $discover block as a change to the file and explains each choice.

Ben reads the diff and merges it. The agent cannot widen the scope after that: the caps on calls and time are fixed when the tool server starts.

Step 2

Look

A sweep asks the provider to list each type, then writes the answers into the ledger. It only reads from the cloud and writes nothing to it. pravo asks only for names and ids, and keeps only those: no settings and no secrets.

The agent calls the pravo_sweep tool. It is bounded: the call, shard and time caps were fixed when the server started, and the agent cannot raise them. It uses only the read-only login and the ledger login. It never writes the ledger itself. Only sweep does.

In plain words

The agent presses the same button you would press, on a leash it cannot lengthen.

Step 3

Read the list and sort it

pravo shadow shows what the ledger knows and compares it with what pravo manages. No cloud calls. Notice the line in brackets: the provider leaves some things out on purpose, so a missing item means "not known", not "not there".

The second command above prints one row per object, and --json prints the same rows for a script. Ben looks at the three seen buckets and knows the scratch bucket is rubbish, so he writes an ignore rule. A reason is required. The rule names the exact bucket, not a pattern, because a pattern could hide objects that someone else creates later. He also tells pravo about the platform team's state file, so their bucket shows as "elsewhere".

After the next pravo shadow the bucket row reads seen 1, ignored 1, elsewhere 1, managed 1. After the expiry date the scratch bucket returns to seen and asks again.

The agent reads the table with pravo_shadow (paged, free) and drafts the ignore rule with its reason, as a change to the CUE file. The rule does not merge without a listing of exactly which objects it hides, so the reviewer sees the objects and not only the name.

Names and tags in cloud data are written by whoever can create objects. The agent treats them as data. It never follows an instruction it finds in one.

pravo why aws_s3_bucket:lantern-tmp-export-0912 explains why any object is in its state, for the agent and for you.

Step 4

Pick up, label, check

To adopt a bucket, pravo reads it in memory, writes the CUE that describes it, and runs a check in a scratch copy of the room (assumed feasible; the first spike checks it) before it saves anything. The check asks one question: if I applied this file, would the plan change anything? If the answer is yes, nothing is written.

Four terms in that output. Specified is the number of settings the CUE spells out. Inherited is the number of optional settings the provider fills in that the CUE leaves out. Pinned means pravo wrote down the value it observed because the first check showed a difference. Frozen by profile means a setting the provider chooses by default that pravo wrote down anyway, so a later provider upgrade that changes the default shows up as a difference.

The machine and the database go through the same steps, one command each: pravo adopt --from-ledger --type aws_instance and pravo adopt --from-ledger --type aws_db_instance. The same code runs for one object and for fifty. A batch is capped at about 50 so a person can read it.

The agent calls pravo_adopt_print. It runs the same adoption but writes nothing, not even a file. It returns the shape: attribute names, counts and the gate result. The values are replaced, because a generated file is a literal copy of the cloud object and a tool result goes to a model provider.

With values hidden, the agent can still do useful work. It proposes the ids file and the addresses, notes which objects need a pin, and for the database it proposes where the password could come from, for example the company's secret store. It never picks the value. Ben, or the agent with the operator's permission to see values, then runs the real adoption.

In plain words

The agent can describe the toy and suggest the label. It cannot touch the toy, and it is never told the secret.

If a difference is left

After three rounds of pinning, an object can still differ. The design does not write it. It prints the draft and the difference with --print, and you decide. By hand, you copy the draft into the file yourself, fix the setting, and let the ordinary pravo plan be the check, because the saved plan is authoritative anyway. There is no flag that writes a file that failed the check. A command that re-runs the scratch-copy check over a hand-edited file is not designed yet; it is listed as a gap on page 6.

Step 5

Land it as an ordinary change

Adoption is a normal change after this point: a saved plan, a policy, an apply. A policy we would write (adoption-only.cue; not written yet, and whether the policy language can say this is unchecked) refuses any plan that adds, changes, replaces or destroys anything. If the cloud thing changed while Ben was reading, the plan differs from the check and the policy refuses. The answer is to run adopt again, not to apply.

The last line, "planned 0", is the success test. It proves the CUE does not contradict what the provider reads. It does not prove the CUE says everything. Each adoption prints specified N, inherited M, and warns when M is larger than N, because a short label also gives an empty plan.

The agent writes the pull request text from the report file (--report batch1.md): the links, the pins, the holes and what the policy checked. It can run pravo_apply_plan, as today, and only for a saved plan. The policies were fixed when the server started, so it cannot take one away.

A passing check is necessary. A person merging is also required.

Step 6

Prove it, and keep watching

Two things remain. Keep looking, so new things on the floor are noticed. And know how to undo: forgetting a record does not touch the real thing.

There is no daemon. pravo watches only when you tell it to.

After the nightly job the agent reads pravo_shadow and says "two new things appeared". It proposes either an ignore rule or an adoption batch. It cannot merge either one.

For engineers: what this example leaves out
  • All three types here can be listed by the installed aws provider (aws 6.69.1). A type that cannot list needs a file of ids first. See chapter 5.
  • On an older project, records applied before the identity field existed have no identity, and a type with any unmatched record is never shown as seen. pravo state identify adds the field once. Lantern's one managed bucket was created after it existed.
  • The success test is run twice: once as a gate in a scratch overlay, once on the real state after the apply.
  • Three changes to pravo's core come before any of this ships: import must stop writing state at plan time, an adopted record must be protected from the orphan delete that follows removing its text, and two records must never own one object. See decisions and roadmap.

An agent never writes the ledger, the state or the cloud. It never chooses a secret. It never raises a cap or removes a policy. It never applies anything except a saved plan.

With a thousand things the steps are the same and the pace is not

Lantern has three. A bigger company might have a thousand things on the floor. The commands do not change. What changes is how you sort and how many trays you carry.

  • Review scales per rule and per batch, not per object. You read the shadow table, the ignore rules, the batch summary, the links and the pins, and sample the CUE. The gate makes the unread part safe. It does not make it well named.
  • A pattern in an ignore rule needs glob: true and the count it hides, so a later surplus shows up as seen (rule overflow).
  • A failed type does not stop the sweep. Its old entries stay, marked as failed.
  • An agent helps most where the work is repetitive: drafting rules, building the ids file for types that cannot list, restructuring twins into loops. Every proposal goes through the same gate.
Where this gets messyimpractical

For types that cannot list, a thousand things is not manageable by hand

What goes wrong
If the thousand things are spread across thirty types that cannot list, someone has to produce the ids file first. The manual path is complete from the id onward and thin before it.
So we propose
Say so. Ship recipes for thirty aws types chosen from those that cannot list (not yet picked, none written). For the rest, a person, another tool or an agent builds the file. Once it exists the rest is deterministic. Also split roots by account or region before adopting thousands, because every later command reads every record.
