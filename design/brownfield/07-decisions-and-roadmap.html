Before the crew starts, you choose the house rules

The tidy-up crew is ready on paper. Before it walks into the toy room, it needs a few rules from the people who live there.

Should it be allowed to pick up a toy and put it in a box before the grown-ups have read the plan? What should stop a box from being emptied by mistake? Which room do we try it in first? These are not details. Each one changes what the crew is allowed to do.

Explain it like I am five

Each card asks one question, shows the choices, says what each choice costs, and tells you which one we would pick and why.

Every card has three buttons ("I agree", "Not sure", "I would choose differently") and a notes box. What you write stays in this browser. Nothing is sent anywhere. To take the page to a meeting, read the stances back from the cards.

The decisions

Group 1: the blockers

D1

When does an import write the record?

blocker

In toy-room words. Should the tidier be allowed to pick a toy up and put it in a box before the grown-ups have read the plan? If you pick (a): nothing is written until the plan is applied, which is safest, and you will notice that plans now carry the import with them. If you pick (b): a small mark protects half-adopted records, and the risk is that every part of pravo must remember to honour it. If you pick (c): you accept the orphan and write the warning down.

Today pravo plan writes the record for an $import before anyone reviews the plan. With agents planning and a thousand objects, an abandoned adoption leaves an orphan record, and the next plan proposes deleting the real object.

(a) Carry the import in the saved plan recommended

An unreviewed plan writes nothing. The import takes the address lock. At apply, the import reads the object again and compares it with the state recorded in the plan.

  • Safest result
  • Largest change. It changes the documented property "a plan is not read-only"
  • Without the apply-time re-read and the stale exit code (3) it breaks "applied exactly as reviewed"

(b) A pending_adoption mark, as a stopgap

The record carries a mark that the orphan delete never touches. pravo state can list and clear it.

  • Much smaller change
  • A mark every code path must honour
  • A new record field, so it raises the D5 question

(c) Document the hazard

Change nothing. Warn in the docs.

  • No work
  • Ships a known trap that deletes real objects

Recommendation. (a). Use (b) only as a bridge for the first release if (a) slips.

D2

What protects an adopted record from the orphan delete?

blocker

In toy-room words. Once a toy is in a box, taking the label off the box must not make the tidier throw the toy away. If you pick (b): a protected box with no label is an error, never a quiet deletion, and removing protection becomes a reviewed change of its own. If you pick (a): the old protection stays and a deletion can still slip through.

prevent_destroy guards only declared resources. Remove the text of an adopted resource and the next plan deletes the real object.

(a) prevent_destroy only

Rely on what exists today.

  • No new mechanism
  • Does not stop the delete when the declaration is removed

(b) Copy the protection into the record recommended

A protected record that is not declared makes the plan an error. destroy refuses too. Unprotecting is its own reviewed change: declare prevent_destroy: false, apply, then remove the text, or run pravo state rm.

  • The "allow delete" decision lives in the saved plan and never in a flag
  • A new record field, a format question and a new plan error
  • An older binary may drop the field without a warning (unverified)

(c) An observe-only record mode

A record that can be read and never changed or destroyed.

  • A stronger guarantee
  • Much more invasive; new record semantics

Recommendation. (b), once phase 0 settles two preconditions: whether an older binary keeps an unknown record field, and the format. If it can drop the field, the safe option is a format bump to 2 that older binaries refuse. That makes D5 the price of D2(b).

D13

How do we stop two records owning one object?

blocker for bulk

In toy-room words. Two boxes must never claim the same toy, because emptying one box would then take the toy out of the other. If you pick (a) with (b): the second claim is refused, both when you plan and when you save. If you pick (c): people have to notice by reading, and one day nobody will.

Two addresses with one $import id take two locks and both import. Destroying either record then destroys the other's object. This is the one failure that deletes real infrastructure.

(a) A commit-time identity lock recommended

A record written from an import takes a lock keyed by canonical identity, or by provider, type and import id, and is refused when another record holds it.

  • Catches two branches and overlapping runs inside a root
  • A second lock kind; changes "one lock per resource"
  • An id-only key can miss a differently formatted id for the same object

(b) A plan-time check recommended with (a)

Two $import entries in one specification that resolve to one identity are an error (exit 6).

  • Cheap
  • Does not cover two branches, two runs or two roots

(c) Review only

Rely on people to notice.

  • No work
  • A thousand objects is too many to notice

Recommendation. (a) and (b) together. Across roots nothing is detected; that stays open in D4.

D7

Which provider first, and who provides a sandbox account?

blocker for phase 0

In toy-room words. Before we build, someone must watch the caretaker read out a real floor, once. That needs a real room to practise in. If you pick (a): we use an aws test account that can only look. If you pick (c): we practise on a pretend room, and every claim about the real one stays a guess.

Without a real account nobody can watch a list stream finish. Every claim about list events, timing and identity import stays unverified.

(a) aws, with a read-only sandbox account recommended

aws is the only list-capable provider on the test machine. The account needs read-only access. Roughly a day or two of someone's time (an estimate).

  • Measures the unknowns that matter most
  • Someone has to create and pay for the account

(b) azurerm or google first

The next candidates by documentation page count. awscc lists about 75 percent but through Cloud Control with different CUE types.

  • Tests a second provider's behaviour
  • Neither is cached on the test machine, so nothing about their list behaviour was observed

(c) No sandbox: build against a fake provider only

Phase 1 does not need a real list. Phase 2 and 3 would be built on guesses.

  • No account to arrange
  • The ledger key and stream handling rest on events nobody has seen

Recommendation. (a). Phase 1 can start without it, but nothing about listing can be trusted before it.

Group 2: structure

D3

Where does $discover live?

open

Scope, ignore rules and known states need a home in the specification.

(a) A top-level field in the specification recommended

One place for scope, rules and known states.

  • Easy to find and review
  • Placement is a build-time check, not yet tried

(b) A meta field on the provider struct

Scope falls out of the instance.

  • Neat for scope
  • Splits rules from scope
  • How provider structs treat $ fields is unverified

(c) A sibling file named on the command line

Like policies today.

  • Leaves the specification untouched
  • Decisions are easy to miss

Recommendation. (a).

D4

One ledger per root, or one per account?

open

The shadow estate belongs to the account, but "managed" is relative to a root.

(a) Per root in the first version recommended

Keys are built to merge later.

  • Simple
  • Repeats sweeps across roots
  • Cannot see other roots, so no cross-root double-adoption check

(b) A shared ledger on a named backend

Plus a per-root list of identities.

  • Also detects cross-root double adoption
  • A bigger design

Recommendation. (a), and keep (b) in phase 5.

D5

Do we bump the store format? Two questions, not one.

open

The ledger is a rebuildable cache. A new field on records (protection, identity, a pending mark) is not.

(a) Ledger: no bump recommended

Older binaries ignore an unknown inventory/ directory.

  • Older pravo keeps working
  • An old state pull drops the ledger: one re-sweep and the first_seen history lost

(b) Ledger: bump when inventory/ first exists

Older binaries refuse the store.

  • Nothing is dropped silently
  • Locks older pravo out of the whole store

(c) Records: bump to 2 for protection recommended

Unless phase 0 shows that an older binary keeps unknown fields.

  • Protection cannot vanish without a warning
  • Older pravo is locked out
  • ARCHITECTURE.md says "2, or 3" and the code says 1; reconcile first

Recommendation. (a) for the ledger and (c) for protection, unless phase 0 proves an older binary keeps unknown record fields.

D6

Can an adopted record settle without an apply?

open

An adopted record has no dependency edges or config hash until an apply, so until then every later plan re-reads it.

(a) Accept "adoption ends with an apply" recommended

Even a zero-change apply writes the edges.

  • No core change
  • One more step per batch

(b) Let a plan write them when an imported record matches

Removes the extra apply.

  • Fewer steps
  • Touches the core "unchanged" decision and can mark a record settled that is not

Recommendation. (a).

Group 3: scope and defaults

D8

How do we cover several regions?

open

A provider instance is one account and one region. An account-wide aws sweep touches many regions.

(a) One declared provider instance per region recommended

Verbose. Per-region instances work for plan and apply today; sweeping through them is untested.

  • Predictable
  • Up to 17 provider processes, capped by --instances

(b) The region list attribute on one instance

233 of 253 aws list types have it.

  • One instance
  • Unverified; nobody ran it
  • Adopted resources need region pinned in CUE or their read goes to the wrong region

Recommendation. (a) for the first version; (b) is phase 5.

D9

Do we offer observe-only rights in the first version?

open

Other tools offer a ladder of rights from observe to update to delete. It is a good idea and a large change.

(a) No recommended

Use prevent_destroy and the D2 mark.

  • No new record semantics
  • No true watch-only object

(b) No, but document a watch-only recipe

ignore_changes plus prevent_destroy plus a policy.

  • Cheap, and a reader gets something
  • ignore_changes: "*" over nested blocks is unverified

(c) Build observe-only records

A new record mode.

  • Strongest guarantee
  • Much more invasive

Recommendation. (a), with (b) as an optional documentation extra.

D10

Do we use the provider's own GenerateResourceConfig?

open

One of the seven cached providers offers it. It was seen only on a synthetic state and still returned tags_all.

(a) Not in the first version recommended

pravo's own generator is the only path.

  • One path we own and can test
  • Identical behaviour for every provider

(b) Use it as the main generator

Let each provider decide.

  • Less code of ours
  • A second generation path has produced wrong output before

(c) A second opinion later

When the capability bit is set, compare.

  • Extra signal
  • Phase 5, after real reads exist

Recommendation. (a), and revisit (c) when real reads exist.

D11

What do we do about the numbers we guessed?

open

Batch cap 50, pin rounds 3, list limit 10,000 per shard, sweep age 7 days, unlisted pruned after 30 days, sweep parallel 4, sweep instances 2, adopt parallel 1, exit codes 7 and 8. All are assumptions.

(a) Ship them as flags with these defaults recommended

Tune after phase 0.

  • Nothing blocks
  • Early users meet guessed defaults

(b) Hold the release until measured

Wait for real data.

  • Better defaults
  • Later release; needs the sandbox from D7 first

Recommendation. (a).

D12

Which test provider do the docs and tests use?

open

Docs are verified by running every command, so each page needs a provider that works with no cloud account. None of the cached providers can list.

(a) Both, fake first recommended

A small in-repo fake that can list, then recorded replay.

  • Fast tests now, real shapes later
  • Two things to maintain; a recorded stream is a new kind of record

(b) A fake only

Hand-written events.

  • Cheapest
  • Tests our guess of a stream, not a real one

(c) Recorded replay only

Record streams from the sandbox and replay them.

  • Real data
  • Needs D7 first; nothing to test with before it

Recommendation. (a).

D14

How do we detect objects another controller owns?

open

Objects managed by CloudFormation, autoscaling, EKS or Elastic Beanstalk carry marker tags. The exact tag names were not verified in the study.

(a) Ship a marker list as editable CUE data recommended

Start with aws, after phase 0 reads the aws documentation. A hit blocks the object unless --allow-owned.

  • Catches common mistakes at adopt time
  • A list to maintain per provider
  • It is detection by marker, not proof that no owner exists

(b) No marker check; review only

Leave it to ignore rules and known states.

  • Less to build
  • Adopting another controller's object puts two controllers in a fight

Recommendation. (a).

Six phases, in order, with no dates

Explain it like I am five

First we check the floor is safe, then we teach the crew to pick up toys you name, and only later to walk round and find toys for itself.

The phases are an order, not a schedule. Any duration would be a guess, because phase 0 needs an account that does not exist yet and measures about twenty unverified behaviours.

  1. Phase 0, next

    Spike on a read-only aws sandbox

    Watch a full list stream finish. Measure event contents, display names, ordering, limit, latency, the crash on an unconfigured list, identity-only import, read with identity, and whether list output equals read output. On pravo itself: does an older binary keep an unknown record field, does $discover fit as a top-level field, is an overlay backend cheap.

    Blocked on: D7, a sandbox account. Nothing is blocked on providers: the spike is what tests them.

  2. Phase 1

    Core changes first, then adoption by id

    Order: D1, D2 with its format decision in D5, D13, the import marker on the plan document, the pravo import rewrite, state identify, the state rm warning. Then the generator, the provider-level gate, the overlay gate, references, --order, --relink, --resume, holes and the report. Then pravo adopt TYPE ID and --ids FILE, the recipes folder for thirty aws types, docs and a runnable example with random or local.

    Provider support needed: none. It works with every provider that imports. Blocked on: our own decisions D1, D2, D5, D13. It is not small: it changes pravo's core.

  3. Phase 2

    Plugin layer: list and identity

    Hand-written client stubs for protocols 5 and 6, including a streaming list call (the client has unary calls only). Capability detection that tolerates Unimplemented. Schema cache version moves. shadow --coverage and schema --list work without a sweep. Identity-form $import if phase 0 supports it.

    Blocked on providers: only providers that implement list. Today that is aws 6.69.1 among the cached ones.

  4. Phase 3

    Ledger and sweep

    inventory/ store with manifests, sweep, shadow, $discover, ignore rules, known states, --due, --plan, exit codes, adopt --from-ledger, why, the record identity field and matching.

    Blocked on providers: the list part covers only listable types. The file door works for any provider.

  5. Phase 4

    Agent layer

    MCP tools (pravo_shadow, pravo_sweep, pravo_adopt_print, extended pravo_why and pravo_schema), a brownfield section in the skill, docs and example policies.

    Provider support needed: none beyond what earlier phases used.

  6. Phase 5, later or risky

    The long tail

    Parent edges in $discover, region fan-out on one instance, the provider's config generation as a second opinion, a shared ledger and cross-root registry, observe-only rights, a twins report, settling without an apply, tag rules.

    Blocked on: real data from phases 0 to 3, and on providers for the parent edges.

In plain words

The first release will list only a minority of types, and it can still onboard any type if you give it the id.

What we would build first, and how we would know it works

Explain it like I am five

We would start with the safest small thing, picking up one named toy, and we would only say it works when the list matches the room.

Build the spike, then phase 1. The first useful thing a user gets is pravo adopt TYPE ID and --ids FILE behind the empty-plan gate, for any provider that imports. Everything else builds on it.

The success test

An empty plan after onboarding: 0 to add, 0 to change, 0 to destroy for the batch, and a second plan after the apply reaches zero. It proves the CUE does not contradict what the provider reads, and no more.

For engineers: what would make us stop and rethink
  • A real list event fills identity fields differently from a read, so the ledger key does not match records.
  • An older binary silently drops a new record field and the format bump is refused.
  • The overlay backend is not cheap, and the fallback of a temporary local backend is too slow for batches of 50.
  • Provider calls per adopted object are far above the estimate of 8 to 12.
  • Identity-only import does not work on aws, so the id path carries everything.

What the review changed

Explain it like I am five

Someone whose job was to find holes in the plan found twenty, and we fixed most and wrote down the ones we could not.

An adversarial review of the first version found 3 blockers, 11 majors and 6 minors. Every blocker and major is accepted in substance. Where the fix differs from what the review proposed, or a limit remains, it is said below.

Where we did not take the reviewer's fix

  • Bump the format to 2 as the cure for finding 2. Offered, not decided: it locks older binaries out of the whole store, so it stays your call in D5.
  • Identity lock for finding 3. Taken, but it does not close one object reached by identity and by a differently formatted id, and does nothing across roots.
  • An IAM policy for the ledger. The separate credential is taken. The policy text is not written because nobody tested it, and a local store cannot be separated at all.
  • Recipes "tested in docs." Taken as shipped data, but the documentation build has no cloud account, so recipes can be tested only against a sandbox.
  • Make drift write identity. Rejected: drift finds differences and leaves marks. A separate state identify does the backfill.
  • Serial batches. Described, not fixed.

Still not solved

  • Discovery for types that cannot list.
  • Double adoption across roots.
  • Canonical keys, before a real list event is seen.
  • The calendar cost of serial batches.
  • Every behaviour on the phase 0 list.

The design does not claim otherwise. If you think one of these should block the whole effort, say so on the cards above.
