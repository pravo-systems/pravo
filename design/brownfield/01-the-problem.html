Nobody starts with an empty room

Real cloud accounts are full of things that tools do not know about. That is the problem. This page shows what it looks like, why it hurts, and why the usual fixes are slow.

  • 7 minute read
  • For everyone
  • Engineers: open the boxes marked "For engineers"

The room was never empty

Think of a toy room that a whole street of children has played in for years. Today you are asked to keep it tidy, with a list on the wall that says where every toy lives.

You walk in. Some toys are in labelled boxes, and they are on the list. Many are not. A blue car is under the sofa. A robot is behind the door. A drum belongs to the neighbour.

Nobody can start the list from a clean room. The list has to be written while the room is in use.

Explain it like I am five

"Brownfield" is a word from building. A brownfield site already has buildings on it, so you must work around them. A greenfield site is an empty field. Almost every real cloud account is brownfield.

Two different messes: shadow and drift

People use "shadow infrastructure" and "drift" as if they were the same thing. They are not, and the design treats them differently.

Shadow
A toy on the floor. It exists, and nothing on the list mentions it. In cloud words: a resource that exists in the account and that no record in your state owns.
Drift
A toy that is in a labelled box, but someone repainted it after it was listed. The list says "red car", and the car is now blue. In cloud words: a resource that is managed, but whose real settings no longer match the specification.

pravo already knows about drift: it can find it and leave a mark. What it cannot do today is notice the toys on the floor. That is what this design adds.

Why a messy floor hurts

None of this is dramatic on day one. It gets expensive slowly, and always at a bad moment. These are the four usual ways. They are ordinary reasoning, not measured figures.

  • You pay for what you forgot

    A server nobody remembers keeps running and keeps costing money. It is not on any list, so nobody asks about it.

  • Nobody looks after it

    A storage bucket no one owns gets no review, no tidy-up and no updates. Security teams look for exactly these.

  • You cannot rebuild the room

    If the room floods, you rebuild from the list. A toy that is not on the list is lost. Writing the room down is the point of the list.

  • People become afraid to clean

    If you cannot tell which toys matter, you stop touching any of them. The room grows more cluttered, because tidying feels dangerous.

In plain words

The first job is not to tidy. It is to know what is on the floor.

What people do today, and why it is slow

To bring a toy onto the list you do three things. You find it. You write its label. You check the label is right. Today the tools help with the second and third, a little, and rarely with the first.

Way 1: label each toy by hand

You write the label yourself and tell the tool the toy's secret name, called its import id. You do this once per toy. pravo works this way today, with pravo import ADDR ID or the $import field. You must write the CUE first, and you must already know the id.

Way 2: let the tool draft the label

Two older tools, OpenTofu and Terraform, do the same job as pravo. Both can write a first draft of the configuration for objects you point at, and both label that generation experimental. Drafts also tend to copy every value as a fixed number or word, which is a snapshot, not a design. Nobody ran either tool for this site.

For engineers: the evidence

OpenTofu has -generate-config-out and labels it experimental (research note 2, verified from its documentation). Terraform's documentation also calls generation experimental, and a public issue (number 35178, a Terraform issue) shows it dropping a required nested id. These claims come from the sources in the design's evidence list.

Way 3: ask the provider to list what exists

This is the missing half. A provider can answer the question "what exists?", and the newer tooling asks it. OpenTofu is not there yet; Terraform is. The details are for engineers.

For engineers: versions, dates and issue numbers

OpenTofu first: we found no tofu query in OpenTofu v1.13.2, and the tracking issue (number 3787) was open and marked "pending-decision" on 20 October 2026. That is a narrow claim: we read three Go files, not the whole repository, so check again before you wait for it. Terraform 1.14.0 (19 November 2025) shipped list blocks and a terraform query command that use a listing call in the provider.

Way 4: one-off export tools

Older community tools tried to export a whole account into configuration. At least one of the best known was archived in March 2026, and another is in maintenance mode. Each of them wrote a lot of text quickly. None solved what to do after the text exists.

What a good answer must do

If we are going to build something, five things have to be true. These become the rules of the design on the next page.

  1. See the floor

    Find what is out there and write it down. Never touch it.

  2. Remember it

    Keep the found list, so nobody has to start again each morning.

  3. Let a person decide

    "Ours", "not ours", "later". The decision is text in git, with a reason.

  4. Adopt in batches, with a check

    Write the label, test it, and save nothing that fails the test.

  5. Work with or without an AI

    An agent may help. Every step after the list of ids works by hand, and the check is the same for a person and an agent.

The detail, for engineers

For engineers: ten ways brownfield imports go wrong, and the answer

Brownfield imports fail in ten recurring ways. The design answers each one. The list comes from the research notes behind DESIGN.md, section 2; I did not rebuild it from scratch.

What goes wrong in the fieldWhat the design does
Generated config is a snapshot of literalsGenerate once, flat. Restructuring into modules and loops is a later, separate step under the same check.
Generated config is invalidOwn generator, then validation and a provider-level plan. Failures are listed and never written.
First plan after import is not cleanOmit computed-only values, write optional-and-computed ones, pin what the plan shows differs, at most three rounds.
Secrets cannot be read back, or leak into gitSensitive and write-only values are never written. A required one becomes a visible hole for a human.
Wrong granularity (inline block or separate resource)Reported per type. The choice stays human. Not solved.
Adopting things that belong to someone elseIgnore rules with a reason, states owned elsewhere, a marker check at adopt time. Ownership in general is not solved.
Silent coverage holesA coverage table. "Unknown" is a state of its own.
Tools rotpravo speaks the provider protocol directly, not a command that may change.
Import and config land apart; review does not scaleGate before writing; batches of about 50; review by rule and by batch.
Identity and namingIdentity keys, names derived from the display name, $from to rename.

Two sentences from the design are worth keeping in your head. First: nothing in the listing protocol tells you who created an object, so ownership is detected only by markers and rules. Second: the protocol has no "changed since" call, so every sweep is a full scan.

For engineers: what pravo has today, exactly
  • pravo import ADDR ID and $import adopt one object per call. The CUE must exist first and the import id must be known.
  • pravo state import-tfstate handles only what an existing .tfstate file already knows.
  • pravo drift finds differences for records pravo owns and leaves a durable mark.
  • Nothing lists objects nobody declared, nothing writes the CUE, and nothing remembers what was found.

Source: DESIGN.md section 2, built on a read of the pravo repository by the research notes. I did not re-run these commands for this page.
