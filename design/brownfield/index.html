Tidying a room that is already full

Most teams do not start with an empty cloud. This site explains, from the ground up, how a tool called pravo could find what is already in your cloud, write it down, and help you take it over (the word is adopt) without breaking anything.

What is this, in plain words

The cloud is rented computers, storage and databases that you reach over the internet. A tool like pravo lets you write down, in text files, the cloud you want, then changes the cloud to match the files and remembers what it made.

The trouble is that pravo only remembers what it made itself. Most teams already have things that someone made by clicking in a web page. This site is about how pravo could find those things and take them over, one at a time, safely.

A room, three piles and a tidier

Picture a toy room that many children share. It has been used for years.

Some toys are put away in boxes. Each box has a label on its lid, and a list on the wall says what is in each box. That is the tidy part.

Some toys lie on the floor. Nobody wrote them down. Nobody remembers who left them.

Some toys belong to the neighbour. They are in this room, but they are not ours.

A tidier called pravo arrives. It does not throw anything away. It never walks the room itself: it asks the room's caretaker, which is the provider, to read out what is on the floor. pravo writes that down and waits. A third character, an agent, is an assistant that may point at toys and suggest. It never holds the keys. When you say "this one is ours", it picks the toy up, writes a label, and checks that the label really describes the toy. Only then does the toy go into a box and onto the list.

Explain it like I am five

The cloud is the room. Your list is what pravo knows. The floor is what pravo does not know yet. We want a safe way to move toys from the floor to the list, one at a time, without breaking any.

What this site is, and how to read it

This site is a design, not a product. Nothing here is built. It explains one way pravo could help teams whose cloud already exists, which in practice means almost every team. It is meant to be argued with: every page ends with what is still open.

It is written for two readers. A newcomer who has never used infrastructure as code, and an engineer who will build or review it. So each page starts with a story and plain words, then moves to a part called "For engineers" with the real mechanism, sample commands and the limits.

In plain words

If a page starts to feel like jargon, stop. Go back to the room. Everything here is a picture of picking up a toy, labelling it and checking the label.

One promise runs through all of it, with one honest limit. Every step after you have a list of ids can be done by hand, with no AI. Producing that list for a type the provider cannot list is the one step that needs outside help: a ready-made recipe, another tool or an agent. An agent can help you go faster, and you will see where, but it is never the only road.

The design in ten seconds

Five verbs: look, write down, decide, adopt, prove. The first three never change anything. The last two change only what you point at, and only after a check. Every list of steps on later pages is a closer look at one or more of these five.

  1. Look

    pravo sweep

    Ask the provider (the caretaker) what is on the floor. Read only.

  2. Write down

    pravo sweep

    pravo keeps the names and ids it was told in its notebook, the ledger. The same command does both.

  3. Decide

    pravo shadow

    Read the notebook. Say "not ours, because ..." in a text file. Pick what you want to adopt.

  4. Adopt

    pravo adopt

    pravo picks a toy up, writes its label as CUE, and tests the label against a scratch copy of the room (assumed feasible; the first spike checks it).

  5. Prove

    pravo plan pravo apply

    The plan must say nothing changes. Then the toy is managed. A second plan confirms it.

These command names are proposals. None of them exists yet.

The three decisions that matter most

The full list is on the decisions page. These three shape everything else.

  • A. Keep facts and decisions apart, outside the managed state

    The found list lives in its own place, so pravo can watch the floor and still be unable to throw a toy away. See how the shelves are kept apart.

  • B. Nothing is written until an empty plan has been shown

    The check is a test pravo can run itself. We also say what it proves, and what it does not.

  • C. Adopting by id comes first, listing comes second

    Providers can list only a minority of types today. So the way in must work for a toy you already know about.

Before you get excited: three honest facts

The design is deliberate about what it cannot do. Three facts set the tone. Each carries a badge. Verified means we ran it or read the source ourselves. Unverified means we did not. Assumption means a guess we have said out loud.

The conclusion is not "give up". It is "build adoption by id first, and treat listing as an accelerator". The messy-bits page says the rest plainly.
