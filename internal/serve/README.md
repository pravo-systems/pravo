# internal/serve

`pravo serve` is a read-only viewer: a web server bound to the loopback interface that shows the specification, the state and, when given one, a saved plan as a graph of namespaces and resources. `api.go` is the contract between this package and the browser interface in `web/`. This file fixes the rest.

## Rules that do not bend

1. **Read-only.** The server writes nothing: no state record, no transaction, no lock, no `pravo.lock.cue`, no generated package, no download, no run of a discovery (it suggests the commands that run it), and nothing of the plans stored in the state: it lists and reads them, and takes no claim on one, marks no progress and collects none. A test hashes the project directory and the state before and after a session, with stored plans in it, and requires equal results; another counts the requests that write to a bucket.
2. **Loopback only.** The listener binds `127.0.0.1` (or `::1`). There is no flag to bind another address.
3. **Authenticated.** Each run makes a 128-bit random token. `GET /?token=T` sets the cookie `pravo_serve_<port>` (HttpOnly, SameSite=Strict, Path=/; the port is in the name because a browser shares the cookies of a host between its ports, and two servers would overwrite each other's) and redirects to `/` without the token. Every `/api/` request needs that cookie (any cookie of that name will do: another page of the host can set one with a longer path, which a browser then sends first) or `Authorization: Bearer T`, compared in constant time. A request without it gets 401 and no body that names anything.
4. **Host and origin checked.** A request whose `Host` is not `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>` gets 421. A request with `Sec-Fetch-Site: cross-site` gets 403, and so does a request to `/api/` with `Sec-Fetch-Site: same-site` (a page of another port of the same host). A request with an `Origin` header that is not `http://` and one of those hosts gets 403, for a browser that sends no `Sec-Fetch-Site`. No CORS header is ever sent, and every response carries `Cross-Origin-Resource-Policy: same-origin` and `Cross-Origin-Opener-Policy: same-origin`, so that no other page can embed or read one. At most 32 event streams are open at once (503 after), and each write to a stream has a deadline.
5. **Values are redacted on the server.** A value is sent only when the provider schema says it is not sensitive and not write-only. Nested attributes and blocks follow the schema down; where a record does not have the shape of the schema, a key below an attribute of the schema that is named like a sensitive attribute of it is withheld all the same. When the schema of a type cannot be read, every value of that type is withheld (`redacted: "schema"`). An attribute whose name matches `(?i)(password|passwd|secret|token|private_key|credential|api_key|access_key)` is withheld too (`redacted: "name"`), as a second guard. Sensitive outputs have no value. What a value is held against is decided in one place, `model.judge` (`judge.go`), for every response that sends the value of a node: the attributes of a record and of its history, the changes of a plan, the outputs, the search index and the choices of the template form. A test fails when another file picks strings out of the set. A value is withheld for what it is (the schema, its name, a type with no schema), for what it reads, or for what a provider made. **What it reads:** a top-level attribute or block that the specification sets from a withheld attribute, a sensitive output, a `#Secret` or a `#SecretEnv`, directly or through other fields, is withheld (`redacted: "derived"`, `Output.redacted` for an output, and `Attr.why` names the attribute): a file whose content embeds a password. This is `taint.go`: `specState.computeEdges` records what each field reads (through the provenance analysis of `convert`, `SourceTasks`, which follows a reference to a plain field to what it is built from even when it is concrete, as a string typed into an attribute is, with a resolver that notes the attribute of each reference) and `model.computeTaint` follows it to a fixed point; nothing is compared as text. The grain is the top-level field: a block that reads one sensitive attribute is withheld as a whole. What a person typed into a sensitive attribute (the region in an SSM parameter) travels along these references and by no other way: the same text in a node that does not read it is a coincidence, and it is shown. **What a provider made** is a string in an attribute of a managed resource that is sensitive, computed and not optional (`random_password.result`; `walk.made`). It is unguessable, so it is looked for, as text, in every value of every node (`secretSet.madeOnly`): it can have taken a route that no reference shows, such as a computed attribute that echoes it. The string is looked for as it is and in the forms a specification puts it in: percent-encoded (a connection string), escaped inside a JSON string, hex, and base64 at any alignment (user data). Where a type has no schema, every string of its records counts, as typed. **A data source** reads from outside the graph, such as a file that a resource wrote, so no reference leads to everything it can hold. Its values are also held against the strings, typed or made, of the nodes it depends on, directly or not (`secretSet.withMade`, `model.scopeOf`: the edges of the graph, and what its values were read from through the parameter of a definition), and a field of it that holds one seeds the taint (`model.echoes`, found by the same walk that renders the record): what reads that field is withheld without a look at its text. A node that the specification does not declare has no references to follow and is held against the strings of the nodes it depends on as the state records them, and an output that the state records and the specification does not declare against every string. A text that a person wrote about a node (a line of its source, a value that the specification sets on it, a sentence about it) repeats what was typed, and is held against the strings of the node and of what it depends on besides those a provider made (`model.literals`). A provider that echoes a value that a person typed into a computed attribute of its own has to mark that attribute sensitive, as Terraform asks of it: the text of an attribute is not compared with what was typed anywhere else. A sentence about loading the specification (`SpecError`, the template form) quotes no state, so it is masked only for tags given on the command line (`scrubTags`), and so are the source text of policies and the adopt snippet and acknowledgement entries of a discovery (an identity, never an attribute); the names and ids of a discovery are names. The text of the transactions and locks that are shown (`user`, `actor`, `reason`, `command`) is a name and is not masked against values. In a recorded command line the value of every `-t`/`--tag` is withheld, whether it is written `-t v`, `-t=v`, `--tag v`, `--tag=v` or as a short flag clustered with others (`-vt v`, `-Tt v`, `-vtk=v`), and so is the value of a flag or `key=value` word whose name matches the rule above. The `private` blob, `config_hash` and `provider_config` of a record are never sent. A plan stored in the state is redacted as a plan file is, by the same code: the values of its changes are withheld by the schema, by the name and by the derived rule, and the sensitive values that it would write count as secrets for the values of that plan. What a person wrote into a stored plan (`author`, `reason`, `git_revision`, the actor and hints of its `PlanInfo`) is shown as the history of a record is, and its `command` is masked as a recorded command line is; the reasons of a stale plan can quote a value and are masked against every string. The masking is done against the set of secrets of the plan that is named, which is the state's and the values that plan would write, in every response that is about that plan: the text above, the records of `/api/detail?plan=`, and the lines and tag contributions of `/api/source?plan=`. The listing, which is about no plan in particular, holds only the author; the free text of a plan (`reason`, `command`, `git_revision`) is in the overlay of that plan and nowhere else, because it can quote a value that only the plan holds. Every text that is sent is clipped (4 KiB each) and the part of it that is searched for secrets is bounded (128 KiB), so a plan with a very large field costs the same as a small one.
6. **Source comes from loaded files only.** `/api/source` serves lines of files that `config.Root.Sources` lists, and of no other path; it takes an address, never a path. A file is read only when it still resolves to the path it had when the specification was loaded (a link that was pointed elsewhere since is not followed). A string literal assigned to an attribute that is sensitive for the resource's type, or whose name matches rule 5, is masked in the lines (`"••••••••"`) and the line is marked `sensitive`; so is any occurrence, in a line that is shown, of a string that rule 5 says is a secret (the header of a comprehension, a comment).
7. **Bounded.** Responses cap list elements (`truncated`), attribute text (4 KiB) and source blocks (200 lines each). A record whose values nest deeper than 200 levels is not decoded: its values are withheld and a note says so.
8. **Live without writing.** The server watches the state (the backend's own change signal, or polling every 2 s), the files of `Root.Sources`, the plan file, the plans stored in the state and the readers file, and sends one `change` event on `/api/events` when any differs. The event names what changed: `state`, `spec`, `plan`, `locks`, `plans`, `access` (the readers file), `traces` (the directory of the recorded runs), `discovery` (the runs of the discoveries: for a local state the directory `discovery/runs` by name, size and time; for a bucket its listing and a digest of each object, up to 200 of them, every fifth poll). The stored plans are three objects each below `plans/` (the plan and its summary, which are written once, and the progress, which is replaced), so the watcher signs them cheaply: for a local state, the directory `plans/` by the name, size and time of its entries, as it signs `resources/`, which reads nothing; for a bucket, the listing of the prefix `plans/`, which sees a plan that is stored or collected, and the digest of each progress object (only keys of the form `plans/plan-<hex>.progress.json` are read, up to eight at a time), which keeps its key when it is replaced and which only a plan that something was done with has. A bucket is looked at every fifth poll, as for the records, and the watcher does not hold its lock while the bucket answers: a request that asks for the revision is not kept waiting by a slow bucket. A claim that lapses is scheduled the same way: a plan that a collector hides (its claim holds 10 minutes) shows again, and an apply that left its claim stops counting as running (after 24 hours), without anything being written. A plan that is not applied expires without anything being written, so the nearest expiry of the plans that the last model holds and that are open or stale counts as a change of `plans` when it passes, once. The first event of a stream carries the revision the server holds, with an empty `what`, so that a page that fetched the graph before it connected learns what it missed. It re-reads the state and re-loads the specification then, on the next request.

9. **A sealed state is read with the identity of the command, and shows no value that cannot be opened.** `pravo serve` finds the identity once, with the function that every command uses, when it first reads a state that is sealed: that is while the server is made, before it listens, so that a passphrase is asked for on the terminal there and never while a request is served. The identity stays in memory in the command; `Options` holds the function that reads the protection of the state and no key, and no response holds a key, a lock or an identity. Without an identity, or with one that is not a reader of a group, a record that cannot be opened is listed with its address, type, name, dependencies and revision, `Node.sealed` is set, and no value, no attribute count and no schema are shown for it, whatever the store returned: the model drops the attributes of such a record before anything reads them. The outputs are withheld the same way (`Output.redacted` is `sealed`), and the graph carries one warning that says how many records could not be opened. A state that is not sealed behaves as it did.
10. **The Access view suggests commands and runs none.** `GET /api/access` is built once for each revision of the model from the facts that `Options.Protection` returns (what the store says of its protection, what the readers file says, who the process is) and from fixed templates. A suggestion is a list of steps: a command (one line of `pravo` or `git`, no newline, every argument quoted for a shell as `engine.ShellWord` quotes it), a line to add to or remove from the readers file (the person edits the file; no step is a shell command that edits a file), or a note. A part that the person fills in is an angle-bracket word, never quoted, so that a paste that was not filled in fails in the shell. A reader name reaches a command or a line only if it matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`, the rule that the readers file uses; any other name, from the store or the file, is listed with `name_ok` false and used nowhere, and a name that is shown has its control and direction characters removed and is clipped to 64 characters. A line of the readers file is rebuilt from its parsed parts, never copied, and a line that does not parse is a number and a reason with every quoted token cut, so that a readers file that is a link to a file of secrets leaks nothing. The readers of the store and of the file are matched by reader key, as the locks are. No non-test file of this package imports `os/exec` or starts a process or a client, and a test says so. The page has no control that runs a suggestion.
11. **The Secrets view never opens a value, and needs no key.** `GET /api/secrets` is built once for each revision of the model, from what a sealed state keeps in the clear for each version of a secret (its name, its number, its time and the transaction that wrote it) and from the signatures of those transactions, set against the nodes of the specification that are a `pravo.#Secret` or a `pravo.#SecretVersion` (the name comes from the specification, and the version that a node asks for from its `version`). The server asks the store for the heads and the signers of the versions (`Store.Secrets`, which lists without a key) and never for a value or a note: a test fails when a non-test file of the package names a function of the store that opens or writes a secret, and another plants a value in a sealed state and in the specification and searches every answer of the server for it in the clear, in base64 and under a store whose identity could open it. The values are not in the answers because they are not read, which is a stronger thing than being masked. A node that reads a secret has no record, so `Detail` shows its schema, the name, the number of the version that the state holds and a note, with `value` withheld as sensitive; `Source` shows the lines of the specification. A name that a bucket object has and that is not a valid secret name was not put there by pravo: it is cleaned of control and direction characters and clipped, and no command is suggested for it. A command that the page suggests is one line of `pravo secret set` or `pravo secret history` with a name that passed the rule of names, and the page runs none. Every judgement is the one the command makes (`state.RecordRules`, the roles chain and the readers file), so the page and `pravo secret list` agree; a state without a readers file lists the versions and judges nobody (`checked` is false, and one issue says so). The answer is bounded: 2000 versions are judged one by one (a state with more is judged by the latest version of each secret, and says so), 20 items are listed under an issue and 40 nodes under a secret.

12. **The chat reads what the page reads, and nothing else, and is off unless it was asked for.** `Options.Chat` is nil unless `pravo serve --chat` was given, and then `POST /api/chat` and `GET /api/chat/config` exist; without it the first is 404 and the second says `enabled: false`, and the page draws no control. The model is offered the tools of `chatTools` in `chat.go` (overview, search, node, source, plans, plan, policies, discovery, secrets, access, traces, trace), each a fixed GET of a path of this server, run in the process with the token of the run, so a request goes through the same checks and the same redaction as one of the page (rule 5, and rule 11 for the secrets: no value is read, so none can be sent). An argument that a tool does not list is refused, a tool that is not listed is refused by the loop before anything runs, and no tool applies, approves, stores, collects, locks, adopts, plans, refreshes or reads the value of a secret: the tests require the set of names, that every path is one the page reads, that `chat.go` imports no `os/exec`, `engine`, `state` or `protect`, that `internal/chat` imports nothing of pravo, and that a model that asks for every write it can name changes no byte of the project and is sent no secret (nor a string that rule 5 withholds) in any answer of a tool or request to the provider. A tool answer is clipped at 32 KiB, a question makes at most 12 reads and 128 KiB, four questions can be open, and the body of a question is at most 64 KiB, `application/json`, with a conversation that ends in a question; the page holds the conversation and the server holds none and writes none. The key is read by the command from `ANTHROPIC_API_KEY` or `PRAVO_CHAT_API_KEY` and is held by the provider only: no response, no event and no error text carries it, and a redirect to another host than the configured one is refused. The endpoint is `https`, or `http` on this machine. This is the only request of the server that reaches another host. Every answer ends with the ledger of what was sent: each read, its arguments and the text, as it went into the request.

## Endpoints

| Path | Response |
|---|---|
| `GET /` and `/assets/...` | the embedded interface (`web/`), no data |
| `GET /api/ping` | `{"ok":true,"version":N}` |
| `GET /api/graph` | `Graph` |
| `GET /api/detail?addr=A` | `Detail`; with `&plan=ID` it answers for that stored plan, with `&plan=none` for no plan |
| `GET /api/source?addr=A` | `Source`; `&plan=ID` marks the lines that stored plan changes |
| `GET /api/plans` | `PlanList`: the plans stored in the state, newest first |
| `GET /api/plan?id=ID` | `PlanOverlay`: a stored plan laid over the graph, as `--plan FILE` lays a plan file, with the text its author wrote (`reason`, `command`, `git_revision`), masked |
| `GET /api/search?q=Q` | `Search` |
| `GET /api/access` | `Access`: how the state is protected, who can read it, the readers file against the store, and suggested commands to copy |
| `GET /api/secrets` | `Secrets`: the secrets that the sealed state keeps (name, version, when, who signed it, whether a key that may write accounts for it), set against the nodes of the specification that read them, and what is wrong, worst first. Never a value, and no key is needed |
| `GET /api/discovery` | `Discovery`: the discoveries of the specification, what their last runs found, and what each found object is to the state: unmanaged, adopting, acknowledged. The managed ones are counted and not listed |
| `GET /api/adopt?discovery=NAME&key=KEY` | `Adopt`: the CUE that adopts one object of the last run of a discovery, and commands to copy. 404 for an object that is not in the run or is managed |
| `GET /api/traces` | `TraceList`: the runs that pravo recorded in `.pravo/traces` (or `Options.TraceDir`), newest first, at most 200, with a summary of each. Read from the directory, whatever the project loads as |
| `GET /api/trace?id=ID` | `Trace`: the spans of one run, with texts masked against the secrets of the state. 400 for an id that is not `<32 hex>-<16 hex>`, 404 for a run that is not there, 422 for a file that is not a run |
| `GET /api/chat/config`, `POST /api/chat` | `ChatConfig`; and with `--chat` the stream of an answer (`read`, `text`, `done` with the ledger, or `error`). See rule 12 |
| `GET /api/events` | `text/event-stream`, event `change`, data `Event`; a comment line every 15 s |

All responses are `Cache-Control: no-store`. `addr` is URL-encoded. An unknown address is 404 with `{"error":"..."}`. An `id` or `plan` that does not have the form of a plan id (`plan-` and six or more hexadecimal digits) is 400; one that no stored plan has is 404. The id is looked up among the plans that the server lists and is never used as a path, and the beginning of an id is not taken for it. Everything about the stored plans is additive: `Node.plans`, `Node.overlap` and `PlanInfo.id`, `PlanInfo.status` are new fields, and a client that does not know them reads the rest as before.

## Meaning

* A **namespace** is every proper prefix of a node address that holds a resource below it (an instance of a definition, a package instance, a plain struct). `Node.Namespace` and `Namespace.Parent` carry the tree: the page never parses an address.
* **Modes**: a node is `managed`, `data`, `ephemeral`, `call`, `builtin` (an environment variable, a remote state) or `output`.
* **Presence**: `both` (declared and recorded), `spec` (declared only), `state` (recorded only: an orphan the next apply would destroy).
* An **output** of the root is a node with `Mode` and `Type` `output`, at its address (the path it sits at) and in the namespace of that path. It is not a resource: it has no record, so no revision, history, lock or refresh time, and no count of resources includes it (`Namespace.Resources`, `PlanInfo.Total`, the "planned N of M" and "not read" of the page); `Namespace.Outputs` counts the outputs below a namespace, and a namespace that holds only outputs has no resources. Its presence is about its recorded value in the outputs of the state: `both`, `spec` (declared, no apply recorded it) or `state` (recorded, not declared). Its edges run from what its value reads, found as for a resource (`convert.Dependencies` with the specification as resolver, outputs counted as tasks, so an output that reads another is joined to it). `Node.Sensitive` is 1 when its value is withheld. `/api/detail` has one attribute, `value` (type `output`; withheld as `sensitive` or `derived`, "known after apply" when no value is recorded), and `description` when the output has one; `/api/source` has the lines of the declaration. A plan lists the value of every output and does not say which it changes, so `Node.Action` of an output is always empty. A recorded output whose address is the one of a record in the state is not a node: the record keeps the address, and a warning says so.
* **Edges** run from the dependency to the dependent. They come from the specification where it loads and from the state records where it does not.
* **Plan**: `--plan FILE` reads a saved plan, shows its actions on the nodes (`Node.Action`) and the attribute changes in `Detail.Change`. A stale plan is shown with its reasons. The viewer never creates a plan itself.
* **Stored plans**: a plan that someone made with `pravo plan --store` lives in the state, as `plans/<id>.plan.json` (the plan, in the format of a plan file), `<id>.meta.json` (its summary) and `<id>.progress.json` (what has been applied from it, and who is using or removing it). The server lists them whether or not it was started with `--plan`; `--plan ID` (an id, or the beginning of one, that is not the name of a file) lays one over the graph from the start, as `Graph.Plan` and `Node.Action`, with `PlanInfo.id` set, and any other stored plan is laid over by the page through `/api/plan` and the `plan` parameter of `/api/detail` and `/api/source`. `--plan ID` does not take the tags of the plan; give `-t` as for `pravo plan list`.
  * `StoredPlan.status` is `pending`, `partial`, `partly-stale`, `stale`, `applied` or `expired`, judged as the listing of the command judges it, against the state that is shared: its lineage and the revision and generation of the nodes the plan changes. The configuration and the providers belong to one working copy, and `pravo apply` checks them; the viewer does not. `open` is set for `pending`, `partial` and `partly-stale`.
  * A `partly-stale` plan is one whose unapplied changes partly conflict with the state (the engine's `PlanPartlyStale`). It is open, and not stale: `PlanInfo.stale` is not set and it has no `reasons`. `StoredPlan.conflicts` lists the changes that cannot be applied now, `{addr, reasons}` sorted by address, 20 at most (`conflicts_omitted` counts the rest; each reason is masked and clipped as a stale reason is), and `unapplied` is how many changes the plan has left, the conflicts included. `apply_only` is the part that can be applied, sorted, a closed selection for `pravo apply --only` (2000 at most, `apply_only_omitted` for the rest), and `apply_live` is the command that applies it, `pravo apply ID --only a,b,c`, worded by the engine (`PlanEntry.OnlyFlag`); it is absent when the command would be longer than 16 KiB. `PlanChange.conflict` marks, in `touches`, each change that is left and cannot be applied. In `Detail.Notes` for a stored plan, a conflicting change says why.
  * `Node.plans` lists, newest first, the open plans that still have a change to apply on the node, and `Node.overlap` is set when two or more can apply it: applying one makes the other stale. A plan that is stale, applied or expired is not on a node, and neither is a plan on a node whose change it has applied (`PlanChange.applied`). A partly stale plan stays on the node of a change that conflicts, which it cannot apply: that change does not count for `Node.overlap` or `StoredPlan.overlaps`, as it does not in `pravo plan show`. The same set of unapplied, de-duplicated addresses feeds `Node.plans`, so it and the overlaps agree, less the conflicting changes. `StoredPlan.overlaps` names the other open plans that can apply a change on a resource this plan can apply one on, and the relation is symmetric: `{id, count, addrs, truncated}` carries the number of such resources, the first 20 of them, and how many are left out.
  * The listing is bounded: `touches` has at most 2000 changes (`truncated` counts the rest), `reasons` and `conflicts` at most 20, each reason clipped to 300 characters (`reasons_omitted` counts the rest; `PlanInfo.reasons` and `PlanInfo.hints`, capped the same way, end with "and N more"), and the author is clipped to 4 KiB. The list is computed once for a model and shared by every request for that revision. The listing has no `reason`, `command` or `git_revision`: the overlay carries them (see rule 5).
  * What is read of a stored plan is bounded: a summary over 8 MiB, a progress object over 1 MiB or a plan over 256 MiB is refused (`engine.ErrTooLarge`, naming the plan and the size), and the plan is listed in the warning for plans that cannot be read. The size is known once the object is read, so it is transferred once and not decoded. Summaries are written once, so the server keeps what it read of each by plan id between rebuilds (a summary, or the refusal of it) and forgets the plans that are gone; the progress, which is replaced, is read each time.
  * A plan whose objects cannot be read, or whose id is not valid, is not listed; the graph carries one warning that names up to five of them (the id and a short reason, with anything the object quoted left out), so that a person who looks for a colleague's plan can tell why it is not there.
  * `StoredPlan.apply` is `pravo apply ID` (and `apply_live` for a partly stale plan): the page copies it and applies nothing. The viewer has no control that approves, applies or removes a plan. The command carries no `-t` or state selector, since the server does not print one anywhere else.
  * The overlay of a plan is worked out the first time a request asks for it, with the cached schemas and no provider, and kept for the revision. Without a cached schema the actions and counts are shown, with a warning, and not the values. The overlay of a plan has its own set of secrets (those of the state and the ones the plan would write), so that a plan does not change what another plan's values are judged against.
* **Access**: `Access.state` is `off` (format 1), `immutable` (format 2), `sealed` (format 3) or `migrating`. `Access.readers` lists the readers of the current group of the store and of the readers file, matched by key, with `in_file` and `in_store`; `Access.file.verdict` is `match`, `differs` (`added` are the readers in the file and not in the store, `removed` the reverse: a rewrap makes the store match the file), `missing`, `invalid`, `expected-sealed` (the readers file loads and the state is `off` or `immutable`: the repository expects a seal that the state does not have, and the first suggestion is `check-downgrade`) or `none` (the state is not sealed and there is no file to expect a seal from). `Access.you` is `reader`, `not-reader`, `no-identity` or `locked` (the identity is sealed with a passphrase and none was available). The readers file is looked for in `Options.AccessDir`, else in `.pravo/access` of the project directory and of each parent up to the one that holds `.git`, and its resolved path is what the watcher signs. The suggestions are `seal`, `check-downgrade`, `finish`, `identity`, `rewrap`, `add-reader`, `remove-reader:NAME` (at most 50), `reseal` and `status`; `primary` marks the next step for the state shown.
* A **secret** is a named value that a sealed state keeps for its readers, as numbered versions (`secret/NAME@N.json`: the value is sealed, the name, the number and the time are not). `Secrets.secrets` has one entry for each: `status` is `set` or `removed`, `version` the latest, `versions` how many there are, `by` and `at` who and when, `trust` whether a signed record of a key that may write accounts for it (`ok`, `vouched`, `unchecked`, `unconfirmed`, `problem`), `bad` how many older versions are flagged, and `used_by` the nodes of the specification that read it (`pin` when a node asks for a version, `number` when it reads only the number). `Secrets.issues` are the things that need action, worst first, each with the secrets it names and the command that mends it: `unsealed` (the specification reads secrets and the state is not sealed), `unreadable`, `roles` (the roles do not verify), `unset` (a node reads a secret the state does not hold or that was removed), `untrusted` (a version that no signed record of a writer accounts for), `unchecked` (versions signed by a key that the readers file does not list) and `unchecked-all` (no readers file, so nobody is judged). `Secrets.all_clear` is the one line that says so when there is no issue and there are secrets, and `Secrets.problems` is the number of issues, which the tab shows when it is not zero. A `pravo.#Secret` is a node of mode `ephemeral` and type `secret`, a `pravo.#SecretVersion` a node of mode `builtin` and type `secret_version`; neither has a provider or a record, and both stand in the first column of their lane, as an environment variable does.
* A **discovery** is a list resource type of a provider with the scope to list it in (`$provider.#Discovery.<type> & {...}`), and `pravo discover` runs it and keeps what it found in the state (`discovery/runs/<name>.json`). The viewer asks no provider and runs nothing: it sets the last run against the records, the `$import` declarations and the `$ack` entries of the discovery in the specification. An object is `managed` when a record of the same type has the same values for the identity attributes the record also carries, and at least one of those is not a scoping attribute (`region`, `account_id`, ...); managed objects are counted and never listed. The rest are `unmanaged` (they ask to be adopted), `adopting` (a resource names them in `$import`) or `acknowledged` (an `$ack` entry covers them: it is shown, quietly, with its reason; `Ack.Ref` names the entry, `$ack[0]`). `Freshness` compares the digest of the scope in the specification with the digest the run was made with: `stale` says that the run answers the old scope. A discovery that only the state holds a run of is `undeclared`; when the specification does not load every discovery is `unknown`. The objects are in the Discovery section and nowhere else: they are not nodes of the graph. Every text that a provider or a person wrote (names, identities, reasons, warnings) is masked against the secrets of the state, stripped of control and direction characters and clipped; at most 2000 objects of a discovery are listed (`items_omitted` counts the rest). `/api/adopt` finds an object by the key the document shows and builds its snippet from the run and the specification. For an unmanaged object it also builds the `$ack` entry that would acknowledge it, as CUE (`Adopt.Ack`; `DiscoveryInfo.AckAll` is the same for all the unmanaged objects when there are at most 50), so that the viewer suggests no command for it. A command it suggests is made only from a name and an id that a shell can carry (no control characters, not long, not starting with `-`), every argument quoted, and a part for the person to fill in is an unquoted angle-bracket word.
* A **recorded run** is a file of `telemetry.RunTrace` that a command wrote (see `internal/telemetry/record.go`): the spans of a command that did some work (a plan, an apply, a discovery, a read of the state; recorded only under `PRAVO_TRACES=on`), with times in microseconds from the start of the run. The server reads `Options.TraceDir` (`.pravo/traces` of the project by default) and nothing else: an id has the form of a run id and names a file of that directory, a file that is not a regular file is skipped (a link is not followed), a file over 64 MiB or of another version is `unreadable`, and an answer has at most 30000 spans. Every text of a run (names, messages, attribute keys and values, event names) is stripped of control and direction characters, clipped, and masked against the secrets of the state as the texts of a transaction are (rule 5); attributes keep scalars and short lists of them. The run does not depend on the model: the list is read when the project does not load, and a run that lands moves no revision. The watcher signs the directory (the component `traces`, by name, size and time), so that the event says `traces` with the revision the page already holds.
* A specification that does not load is shown as the state alone, with `Project.SpecError` set and a warning.

## Interface (web/)

Plain HTML, CSS and JavaScript, no build step, no dependency, embedded with `go:embed`. It uses the site's design tokens (`site/design/css/00-tokens.css`, paper and ink themes) and its fonts. It is one page whose state is in the URL fragment: `#/?sel=ADDR&tab=source&collapse=PATH,PATH&theme=dark&q=TEXT&filter=plan&plan=plan-2f9c1a4e`. A link reproduces the view; the documentation screenshots are made from such links.

## What these rules do not claim

* The token is a bearer secret. It is in the address that is printed, so in the terminal and in the argument list of the browser launcher while it starts. The cookie that carries it is `HttpOnly` and `SameSite=Strict`, but a browser sends a cookie to every port of a host: a server on another port of `localhost` that the browser visits receives it. The token is of no use to a page there (no CORS header, and the checks of rule 4), and a process of the same user can read the project directly.
* Redaction knows what the state and the saved plan hold. A secret that the specification writes as a literal and that no record keeps is masked only where it is assigned to a sensitive attribute, and a secret built from pieces that are not secrets themselves is not found. A secret shorter than six characters is not looked for in other values, and neither is one that is encoded in a way not listed in rule 5.
* A resource that is named after a secret shows the name: an address is a key, and no part of the page can do without it.
* Evaluating a specification is not bounded in time or memory, here as in every command.
* On Windows a program that sets `SO_REUSEADDR` can share a port with the server. The port is random unless `--port` names one.
