# internal/serve

`pravo serve` is a read-only viewer: a web server bound to the loopback interface that shows the specification, the state and, when given one, a saved plan as a graph of modules and resources. `api.go` is the contract between this package and the browser interface in `web/`. This file fixes the rest.

## Rules that do not bend

1. **Read-only.** The server writes nothing: no state record, no transaction, no lock, no `pravo.lock.cue`, no generated package, no download, and nothing of the plans stored in the state: it lists and reads them, and takes no claim on one, marks no progress and collects none. A test hashes the project directory and the state before and after a session, with stored plans in it, and requires equal results; another counts the requests that write to a bucket.
2. **Loopback only.** The listener binds `127.0.0.1` (or `::1`). There is no flag to bind another address.
3. **Authenticated.** Each run makes a 128-bit random token. `GET /?token=T` sets the cookie `pravo_serve_<port>` (HttpOnly, SameSite=Strict, Path=/; the port is in the name because a browser shares the cookies of a host between its ports, and two servers would overwrite each other's) and redirects to `/` without the token. Every `/api/` request needs that cookie (any cookie of that name will do: another page of the host can set one with a longer path, which a browser then sends first) or `Authorization: Bearer T`, compared in constant time. A request without it gets 401 and no body that names anything.
4. **Host and origin checked.** A request whose `Host` is not `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>` gets 421. A request with `Sec-Fetch-Site: cross-site` gets 403, and so does a request to `/api/` with `Sec-Fetch-Site: same-site` (a page of another port of the same host). A request with an `Origin` header that is not `http://` and one of those hosts gets 403, for a browser that sends no `Sec-Fetch-Site`. No CORS header is ever sent, and every response carries `Cross-Origin-Resource-Policy: same-origin` and `Cross-Origin-Opener-Policy: same-origin`, so that no other page can embed or read one. At most 32 event streams are open at once (503 after), and each write to a stream has a deadline.
5. **Values are redacted on the server.** A value is sent only when the provider schema says it is not sensitive and not write-only. Nested attributes and blocks follow the schema down; where a record does not have the shape of the schema, a key below an attribute of the schema that is named like a sensitive attribute of it is withheld all the same. When the schema of a type cannot be read, every value of that type is withheld (`redacted: "schema"`). An attribute whose name matches `(?i)(password|passwd|secret|token|private_key|credential|api_key|access_key)` is withheld too (`redacted: "name"`), as a second guard. Sensitive outputs have no value. A value that the schema does not mark but that contains a string the state keeps in a sensitive attribute (6 characters or more), or the value of a sensitive output, or a sensitive value that a saved plan would write, is withheld too (`redacted: "derived"`, `Output.redacted` for an output): a file whose content embeds a password. The string is looked for as it is and in the forms a specification puts it in: percent-encoded (a connection string), escaped inside a JSON string, hex, and base64 at any alignment (user data). Where a type has no schema, every string of its records counts. The same check masks the text of the transactions and locks that are shown (`user`, `actor`, `reason`, `command`). In a recorded command line the value of every `-t`/`--tag` is withheld, whether it is written `-t v`, `-t=v`, `--tag v`, `--tag=v` or as a short flag clustered with others (`-vt v`, `-Tt v`, `-vtk=v`), and so is the value of a flag or `key=value` word whose name matches the rule above. The `private` blob, `config_hash` and `provider_config` of a record are never sent. A plan stored in the state is redacted as a plan file is, by the same code: the values of its changes are withheld by the schema, by the name and by the derived rule, and the sensitive values that it would write count as secrets for the values of that plan. What a person wrote into a stored plan (`author`, `reason`, `git_revision`, the reasons of a stale plan, the actor and hints of its `PlanInfo`) is masked as the history of a record is, and its `command` as a recorded command line is. The masking is done against the set of secrets of the plan that is named, which is the state's and the values that plan would write, in every response that is about that plan: the text above, the records of `/api/detail?plan=`, and the lines and tag contributions of `/api/source?plan=`. The listing, which is about no plan in particular, holds only the author, masked against the state's secrets; the free text of a plan (`reason`, `command`, `git_revision`) is in the overlay of that plan and nowhere else, because it can quote a value that only the plan holds. Every text that is sent is clipped (4 KiB each) and the part of it that is searched for secrets is bounded (128 KiB), so a plan with a very large field costs the same as a small one.
6. **Source comes from loaded files only.** `/api/source` serves lines of files that `config.Root.Sources` lists, and of no other path; it takes an address, never a path. A file is read only when it still resolves to the path it had when the specification was loaded (a link that was pointed elsewhere since is not followed). A string literal assigned to an attribute that is sensitive for the resource's type, or whose name matches rule 5, is masked in the lines (`"••••••••"`) and the line is marked `sensitive`; so is any occurrence, in a line that is shown, of a string that rule 5 says is a secret (the header of a comprehension, a comment).
7. **Bounded.** Responses cap list elements (`truncated`), attribute text (4 KiB) and source blocks (200 lines each). A record whose values nest deeper than 200 levels is not decoded: its values are withheld and a note says so.
8. **Live without writing.** The server watches the state (the backend's own change signal, or polling every 2 s), the files of `Root.Sources`, the plan file and the plans stored in the state, and sends one `change` event on `/api/events` when any differs. The event names what changed: `state`, `spec`, `plan`, `locks`, `plans`. The stored plans are three objects each below `plans/` (the plan and its summary, which are written once, and the progress, which is replaced), so the watcher signs them cheaply: for a local state, the directory `plans/` by the name, size and time of its entries, as it signs `resources/`, which reads nothing; for a bucket, the listing of the prefix `plans/`, which sees a plan that is stored or collected, and the digest of each progress object (only keys of the form `plans/plan-<hex>.progress.json` are read, up to eight at a time), which keeps its key when it is replaced and which only a plan that something was done with has. A bucket is looked at every fifth poll, as for the records, and the watcher does not hold its lock while the bucket answers: a request that asks for the revision is not kept waiting by a slow bucket. A plan that is not applied expires without anything being written, so the nearest expiry of the plans that the last model holds and that are open or stale counts as a change of `plans` when it passes, once. The first event of a stream carries the revision the server holds, with an empty `what`, so that a page that fetched the graph before it connected learns what it missed. It re-reads the state and re-loads the specification then, on the next request.

## Endpoints

| Path | Response |
|---|---|
| `GET /` and `/assets/...` | the embedded interface (`web/`), no data |
| `GET /api/ping` | `{"ok":true,"version":N}` |
| `GET /api/graph` | `Graph` |
| `GET /api/detail?addr=A` | `Detail`; with `&plan=ID` it answers for that stored plan, with `&plan=none` for no plan |
| `GET /api/source?addr=A` | `Source`; `&plan=ID` marks the lines that stored plan changes |
| `GET /api/plans` | `PlanList`: the plans stored in the state, newest first |
| `GET /api/plan?id=ID` | `PlanOverlay`: a stored plan laid over the graph, as `--plan FILE` lays a plan file, with the text its author wrote (`reason`, `command`, `git_revision`), masked |
| `GET /api/search?q=Q` | `Search` |
| `GET /api/events` | `text/event-stream`, event `change`, data `Event`; a comment line every 15 s |

All responses are `Cache-Control: no-store`. `addr` is URL-encoded. An unknown address is 404 with `{"error":"..."}`. An `id` or `plan` that does not have the form of a plan id (`plan-` and six or more hexadecimal digits) is 400; one that no stored plan has is 404. The id is looked up among the plans that the server lists and is never used as a path, and the beginning of an id is not taken for it. Everything about the stored plans is additive: `Node.plans`, `Node.overlap` and `PlanInfo.id`, `PlanInfo.status` are new fields, and a client that does not know them reads the rest as before.

## Meaning

* A **module** is every proper prefix of a node address that holds a resource below it (an instance of a definition, a package instance, a plain struct). `Node.Module` and `Module.Parent` carry the tree: the page never parses an address.
* **Presence**: `both` (declared and recorded), `spec` (declared only), `state` (recorded only: an orphan the next apply would destroy).
* **Edges** run from the dependency to the dependent. They come from the specification where it loads and from the state records where it does not.
* **Plan**: `--plan FILE` reads a saved plan, shows its actions on the nodes (`Node.Action`) and the attribute changes in `Detail.Change`. A stale plan is shown with its reasons. The viewer never creates a plan itself.
* **Stored plans**: a plan that someone made with `pravo plan --store` lives in the state, as `plans/<id>.plan.json` (the plan, in the format of a plan file), `<id>.meta.json` (its summary) and `<id>.progress.json` (what has been applied from it, and who is using or removing it). The server lists them whether or not it was started with `--plan`; `--plan ID` (an id, or the beginning of one, that is not the name of a file) lays one over the graph from the start, as `Graph.Plan` and `Node.Action`, with `PlanInfo.id` set, and any other stored plan is laid over by the page through `/api/plan` and the `plan` parameter of `/api/detail` and `/api/source`. `--plan ID` does not take the tags of the plan; give `-t` as for `pravo plan list`.
  * `StoredPlan.status` is `pending`, `partial`, `partly-stale`, `stale`, `applied` or `expired`, judged as the listing of the command judges it, against the state that is shared: its lineage and the revision and generation of the nodes the plan changes. The configuration and the providers belong to one working copy, and `pravo apply` checks them; the viewer does not. `open` is set for `pending`, `partial` and `partly-stale`.
  * A `partly-stale` plan is one whose unapplied changes partly conflict with the state (the engine's `PlanPartlyStale`). It is open, and not stale: `PlanInfo.stale` is not set and it has no `reasons`. `StoredPlan.conflicts` lists the changes that cannot be applied now, `{addr, reasons}` sorted by address, 20 at most (`conflicts_omitted` counts the rest; each reason is masked and clipped as a stale reason is), and `unapplied` is how many changes the plan has left, the conflicts included. `apply_only` is the part that can be applied, sorted, a closed selection for `pravo apply --only` (2000 at most, `apply_only_omitted` for the rest), and `apply_live` is the command that applies it, `pravo apply ID --only a,b,c`, worded by the engine (`PlanEntry.OnlyFlag`); it is absent when the command would be longer than 16 KiB. `PlanChange.conflict` marks, in `touches`, each change that is left and cannot be applied. In `Detail.Notes` for a stored plan, a conflicting change says why.
  * `Node.plans` lists, newest first, the open plans that still have a change to apply on the node, and `Node.overlap` is set when two or more can apply it: applying one makes the other stale. A plan that is stale, applied or expired is not on a node, and neither is a plan on a node whose change it has applied (`PlanChange.applied`). A partly stale plan stays on the node of a change that conflicts, which it cannot apply: that change does not count for `Node.overlap` or `StoredPlan.overlaps`, as it does not in `pravo plan show`. The same set of unapplied, de-duplicated addresses feeds `Node.plans`, so it and the overlaps agree, less the conflicting changes. `StoredPlan.overlaps` names the other open plans that can apply a change on a resource this plan can apply one on, and the relation is symmetric: `{id, count, addrs, truncated}` carries the number of such resources, the first 20 of them, and how many are left out.
  * The listing is bounded: `touches` has at most 2000 changes (`truncated` counts the rest), `reasons` and `conflicts` at most 20, each reason clipped to 300 characters (`reasons_omitted` counts the rest; `PlanInfo.reasons` and `PlanInfo.hints`, capped the same way, end with "and N more"), and the author is clipped to 4 KiB. The list is computed once for a model and shared by every request for that revision. The listing has no `reason`, `command` or `git_revision`: the overlay carries them (see rule 5).
  * A plan whose objects cannot be read, or whose id is not valid, is not listed; the graph carries one warning that names up to five of them (the id and a short reason, with anything the object quoted left out), so that a person who looks for a colleague's plan can tell why it is not there.
  * `StoredPlan.apply` is `pravo apply ID` (and `apply_live` for a partly stale plan): the page copies it and applies nothing. The viewer has no control that approves, applies or removes a plan. The command carries no `-t` or state selector, since the server does not print one anywhere else.
  * The overlay of a plan is worked out the first time a request asks for it, with the cached schemas and no provider, and kept for the revision. Without a cached schema the actions and counts are shown, with a warning, and not the values. The overlay of a plan has its own set of secrets (those of the state and the ones the plan would write), so that a plan does not change what another plan's values are judged against.
* A specification that does not load is shown as the state alone, with `Project.SpecError` set and a warning.

## Interface (web/)

Plain HTML, CSS and JavaScript, no build step, no dependency, embedded with `go:embed`. It uses the site's design tokens (`site/design/css/00-tokens.css`, paper and ink themes) and its fonts. It is one page whose state is in the URL fragment: `#/?sel=ADDR&tab=source&collapse=PATH,PATH&theme=dark&q=TEXT&filter=plan&plan=plan-2f9c1a4e`. A link reproduces the view; the documentation screenshots are made from such links.

## What these rules do not claim

* The token is a bearer secret. It is in the address that is printed, so in the terminal and in the argument list of the browser launcher while it starts. The cookie that carries it is `HttpOnly` and `SameSite=Strict`, but a browser sends a cookie to every port of a host: a server on another port of `localhost` that the browser visits receives it. The token is of no use to a page there (no CORS header, and the checks of rule 4), and a process of the same user can read the project directly.
* Redaction knows what the state and the saved plan hold. A secret that the specification writes as a literal and that no record keeps is masked only where it is assigned to a sensitive attribute, and a secret built from pieces that are not secrets themselves is not found. A secret shorter than six characters is not looked for in other values, and neither is one that is encoded in a way not listed in rule 5.
* A resource that is named after a secret shows the name: an address is a key, and no part of the page can do without it.
* Evaluating a specification is not bounded in time or memory, here as in every command.
* On Windows a program that sets `SO_REUSEADDR` can share a port with the server. The port is random unless `--port` names one.
